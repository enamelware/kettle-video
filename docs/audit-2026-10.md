# Code audit, October 2026

A read-only review of the whole codebase on 2 October 2026, at the code as it stood that day. No app code or tests were changed. Each area was reviewed separately. The full test suite was run, and line coverage was measured. Every finding below was checked by reading the code or running it. Anything not fully confirmed is marked **to confirm**.

## 1. Overall verdict

Kettle is in good shape for an app at this stage. The code is small, readable and well documented. The hard safety rule holds everywhere: **nothing in the app can move, rename or delete a media file.** The only files it writes are its own saved library, logs and Firefox profile settings. All 125 automated tests pass. The 3 "expected failures" are known parser gaps that are deliberately recorded as tests. The vendored packages are all used, pure Python (so they run the same on x86 and ARM), and their licences are compatible with the GPL.

The weak spot is **what happens when things go wrong**. The everyday paths work well and are well tested. But several failure cases leave the user stuck on a screen, or close the app with no explanation in Gaming Mode. Examples are an SD card pulled out, a typo in `settings.json`, mpv failing in an unusual way, or a held button. A few docs, including CLAUDE.md, also no longer match what the app does.

No **Critical** problem was found: nothing can damage media files or crash the device. The most serious finding is one level down. Pulling the SD card out during a rescan can empty the *saved library list*, though not the films themselves.

| Area | Health | In one sentence |
|---|---|---|
| Filename parser | fair | Safe and well tested for the patterns it was built for, but plain three-digit anime episode numbers are misread. |
| Library scan and saved library | fair | Clean and safe, but a card pulled mid-scan or one oddly encoded filename can wipe or break the saved library. |
| Playback (mpv) | good | Small, does not block the app, and resume really is mpv's own; one error path leaves "Playing…" stuck. |
| Backend server, settings, dev auto-update | fair | Security basics are solid; settings mistakes produce crashes instead of plain messages, and the server routes are barely tested. |
| UI, controller input, theming | fair | Fast and well built with good browser checks, but failures can freeze the keys or show errors off-screen. |
| Launcher, installer, dev tooling | fair | Careful Firefox handling; errors are invisible in Gaming Mode, and the reviewer agent's read-only guard has a gap. |

## 2. Findings

Sizes: **small** is a few lines in one place, **medium** is a few places or a new piece of UI, **large** is a redesign.

### Critical (could lose data or crash)

None found.

### High (a user would notice)

**H1. Pulling the SD card out during a rescan empties the saved library.**
- What's wrong: the scan checks once at the start that the folder is there. If the card disappears after that, the unreadable folder is quietly recorded as "skipped", the scan counts as a success, and the empty result replaces the good saved library. This breaks the spec's own rule that "nothing is removed". It was reproduced with a temporary folder.
- What the user sees: films or shows vanish from the list until they put the card back and rescan.
- Where: `backend/library_index.py:127` (single check) and `backend/library_movies.py:139-144` (errors become "skipped").
- Size: small. Re-check the folder after scanning; if the top folder couldn't be read, keep the previous entry.
- The same may happen if an unmounted card leaves an empty mount folder behind (**to confirm** on SteamOS and Armada).

**H2. The app can get stuck on "Playing…" with the controls frozen.**
- What's wrong, part 1 (backend): when starting mpv fails for any reason other than "not found", the error isn't caught and the "playing" state is never reset. One example is a configured `mpv_command` that isn't executable. Confirmed by reading the code and by a scratch test.
- What's wrong, part 2 (page): if the backend stops answering or sends back something unexpected while a film is starting or playing, the page never handles the error. Its keys stay locked. Confirmed with a headless-browser probe.
- What the user sees: "Playing…" forever, arrows and A do nothing, every later play is refused as "already playing". Only q works.
- Where: `backend/mpv.py:158-173`, `backend/server.py:250-256`, `ui/js/app.js:508-536`, `ui/js/api.js` (answers aren't checked for errors).
- Size: small.

**H3. In Gaming Mode, start-up failures close the app with no explanation.**
- What's wrong: if Firefox is missing, the backend fails to start, or the port never opens, `launch.sh` only writes to the log and exits. A broken or mistyped `settings.json` is the most likely cause of a failed backend start. This breaks the rule "never fail silently".
- What the user sees: they press Play in Steam, the app opens and closes at once. There is no terminal in Gaming Mode, so there is nothing to read.
- Where: `launch.sh:193-206, 263-266`, `backend/server.py:275-279`.
- Size: medium. It needs some way to show a message on screen; which tool works on both devices is **to confirm**.

**H4. Some settings mistakes give a raw Python error instead of a plain message.**
- What's wrong: these cases each crash with a Python error. All were confirmed by running them:
  - `"movies_path": null` or a number.
  - A settings file that isn't valid text (not UTF-8).
  - An `mpv_command` with an unclosed quote. This also leaves the loading screen spinning forever ("Still working…").
- Two cases are accepted without complaint:
  - An `mpv_command` that is a number, or that points to a file that doesn't exist. It is reported as "mpv available", so the user only finds out when they press Play.
  - An empty folder path, which quietly becomes the app's own folder (**to confirm** what the scan then shows).
- What the user sees: the app closes (see H3), or it hangs on the loading screen.
- Where: `backend/settings.py:51-56`, `backend/mpv.py:30-33`, `ui/js/app.js:570`.
- Size: small.

**H5. Holding a button can skip a screen or quit the app.**
- What's wrong: the key handler doesn't ignore the automatic repeat of a held key. Confirmed by reading the code and with a browser probe.
- What the user sees: holding A on a show opens it and immediately starts the first episode. Holding B in an episode list goes back and then quits the app.
- Where: `ui/js/keyboard.js:52-84`.
- Size: small. Ignore repeats for select and back, but keep them for the arrows.

**H6. Error and status messages can appear off-screen.**
- What's wrong: the banner for "Folder not available", "Playing…" and "Rescanning…" sits at the top of the page and scrolls away with the list.
- What the user sees: far down a long list, they press A and nothing seems to happen. The message is shown, but out of view. Reproduced with 5,000 rows.
- Where: `ui/css/defaults.css:79-90`, `ui/index.html:22-24`.
- Size: small (pin the banner).

**H7. Three-digit anime episode numbers are misread.**
- What's wrong: a name like `Show - 112.mkv` is read as season 1, episode 12. `- 100` becomes S01E00, and `- 098` and `- 007` are read as season 0, so they show up under Specials. It only works when a tag like `[1080p]` follows the number, which is true of every test sample. CLAUDE.md lists absolute anime numbering as a case to handle.
- What the user sees: an anime show with episodes 98–112 appears as "1 season, 3 episodes, 2 specials", with wrong episode labels. This was reproduced.
- Where: `backend/parser.py:163-169`.
- Size: medium.

**H8. One badly encoded filename makes the whole rescan fail.**
- What's wrong: a filename that isn't valid UTF-8 text crashes the scan when the app builds the item's ID. These come from old archives copied onto ext4 cards; exFAT cards are less likely to have them. Reproduced with a scratch file.
- What the user sees: "Couldn't scan the library", and nothing new is saved.
- Where: `backend/library_index.py:32`, and the save just after it.
- Size: small. Skip such files as "name can't be read", like other unreadable entries.

**H9 (development tooling, not users). The reviewer agent's "read-only" guard can be bypassed.**
- What's wrong: `git diff --output=<file>` and `git log --output=<file>` pass the guard, and both overwrite any file. `git diff --ext-diff` also passes, and it can run another program. All were tested by feeding inputs to the hook.
- Separately, test-checker may write a script in `tests/` and run it, and that script could change app code. That is a limit of the approach rather than a bug; it should be written down in `docs/decisions.md`.
- Where: `.claude/hooks/agent_guard.py`.
- Size: small.

### Medium (makes future work harder, or a smaller user-visible issue)

- **M1. Slow rescans with a stuck progress line.**
  - A made-up library of 5,000 films plus 5,000 episodes took 80 s to scan on the Deck, almost all of it in the filename parser.
  - Progress moves in only two big steps, so "0 of 10000" sits on screen for about 40 s.
  - The Nova is likely slower (**Nova risk, to confirm**).
  - `backend/library_index.py:127-137`. Medium.
- **M2. Touch input plays the wrong film.** Tapping a row on the Deck screen highlights it, but A still plays the previously focused row. Reproduced in a browser probe. `ui/js/keyboard.js`. Small.
- **M3. Long filenames run off the side at small 4:3 sizes.**
  - Scene-style names without spaces overflow sideways at 640×480.
  - 1024×768 and 1280×800 are fine.
  - `ui/css/defaults.css:55`. Small. **Nova risk.**
- **M4. Two shows can get the same ID.**
  - A show folder `Foo/` and loose files whose show title is "Foo" get identical IDs (reproduced).
  - Returning focus to the right row could land on the wrong one (the visible effect is **to confirm**).
  - `backend/library_index.py:119-121`. Small.
- **M5. An unexpected disk error can break a request.**
  - The folder check handles "not found", "not a folder" and "no permission" only.
  - Other errors, such as an I/O error from a failing card, escape it. The page then gets a broken answer instead of "Folder not available".
  - The same check is copied in two places: `backend/parsed_library.py:25-41` and `backend/scanner.py:29-44`. Small.
- **M6. In the plain-list fallback view, focus jumps back to the first file after every film.** This was reproduced. `ui/js/app.js:530-531`. Small.
- **M7. Parsing can differ between devices.**
  - The parser reads guessit's optional personal settings files from the home folder (e.g. `~/.config/guessit/options.json`), if one exists.
  - If such a file is broken, every name silently falls back to a plain cleaned-up filename.
  - Parser failures are never logged.
  - `backend/parser.py:147-150`. Small.
- **M8. Logs are never cleaned up.**
  - Every launch adds new log files. There are already 70 files in `logs/` on this Deck.
  - `launch.sh:14-15`. Small (keep the newest few).
- **M9. Leftovers after a force-close.**
  - If Steam kills the launcher outright, its clean-up never runs.
  - The old backend keeps running, and the next launch quietly uses a different port.
  - A leftover Firefox may block the profile (**to confirm**).
  - Medium.
- **M10. The page's start-up logic is repeated.**
  - `main()` repeats the reload and fallback logic (`ui/js/app.js:577-603` vs `288-302, 398-410`).
  - Three functions build the same "heading plus list" layout.
  - "Busy" and "rescanning" are tracked in scattered variables.
  - Medium.
- **M11. Docs and CLAUDE.md are out of date.** Each item was checked against the code:
  - **CLAUDE.md** still describes the MVP as "plain text, no parsed titles" and calls filename parsing post-MVP. The app now parses names and shows the Movies and TV grouping (since the saved library work).
  - **CLAUDE.md** says "The Kettle name and the wordmark font are not applied yet". The loading screen shows "Kettle" in Rubik Mono One (the loading screen work).
  - **CLAUDE.md** says settings are "read and written through the backend". Only reading exists today.
  - **CLAUDE.md** describes theming snippets. They are not built yet (no `themes/` folder, loader or setting). That matches the milestone plan, but nothing says "not yet".
  - **README.md:83-85** ("no parsed titles, no resume") contradicts the rest of the README.
  - **docs/spec.md:5** says folders are scanned at launch; the saved library is loaded instead.
  - **docs/spec.md:45** lists resume as out of scope.
  - **docs/spec.md:47, 59** say the grouping is "not yet used".
  - **Mpv Flatpak SD card access:** `docs/decisions.md:165` says the mpv Flatpak can already read the whole device. `docs/device-setup.md:55-58` and the on-screen hint tell users to add a permission. One of them is wrong (**to confirm** on device).
  - **Theming hooks:** several hooks used by the page are missing from spec.md's list: `.source[data-source]`, `[data-role]`, `#error-banner`, `#playing-status`, `#mpv-missing`, `#loading`, `data-kind="first-scan"`, and the row attributes `data-source`, `data-path` and `data-key`.
  - Small, but worth doing soon, because Claude reads these docs to decide what to build.
- **M12. The installer is a stub.**
  - `install-shortcut.sh` only creates the desktop shortcut, which is still named "Media Player".
  - CLAUDE.md's plan includes checking for mpv, Flatpak permissions and controller steps. That is expected at this milestone, but nothing marks it "not yet".

### Low (tidiness)

- The shortcut breaks if the app folder's path contains a space (`install-shortcut.sh:21`, missing quotes). Small.
- When mpv is missing at play time, the message has no install hint (`backend/server.py:232-234`).
  - The Flatpak-specific hint only appears when the command starts with exactly `flatpak` (`backend/mpv.py:181`).
  - `flatpak info` runs with no time limit on every status check (`backend/mpv.py:20`).
- Malformed requests to the play endpoint get no answer at all, only a log entry. The page never sends these.
  - HEAD requests skip the Host check (they reveal only UI file headers).
  - Unknown `/api/` addresses answer with an HTML page instead of JSON.
- Odd names:
  - `2012.mkv` shows as "2012 (2012)".
  - `Show - 12.5.mkv` gets the episode title ".5".
  - "Season 1 (2004)", "Staffel 2" and "Series 2" aren't recognised as season folders.
  - A file containing two episodes keeps only the first.
- Movie titles don't merge macOS-style accented characters the way TV titles do, so they can sort differently (`backend/library_movies.py` vs `library_tv.py:287`).
- Dead code: `createMinimalQuitController` (`ui/js/keyboard.js:91`).
  - `showParsedLibrary` is marked as waiting for something but never does.
  - `focusFirst` and `focusAt` overlap.
- A few sizes aren't tokens: `max-width: 40rem`, `min-width: 4.5em`, z-indexes, the body font.
- No Home/End or page jumps, so long lists need many presses.
- `launch.sh:143`: on Ctrl+C the clean-up runs twice (harmless).
- The progress total counts videos inside "Sample" folders that the scan itself ignores.

## 3. Test coverage

**How it was measured.** The `coverage` tool isn't installed, and adding it would be a new dependency. So line coverage was measured with Python's built-in `trace` module while running the full suite. The script lived in the scratchpad, outside the repo. Percentages are "lines of backend code run at least once by the tests". The JavaScript and shell scripts can't be measured that way. For them, the table lists which checks exist instead.

**Test run:** 125 tests, all pass, 3 expected failures (known parser gaps), about 35 s.

| Area | Line coverage | Notes |
|---|---|---|
| Filename parser (`parser.py`, `parsed_library.py`, `vendor_path.py`) | **94%** (183/195) | The untested lines are the guessit-failure path and the "folder unavailable" reasons. |
| Library scan and saved library (`scanner.py`, `library_index.py`, `library_movies.py`, `library_tv.py`) | **90%** (527/585) | `scanner.py` 77%, `library_movies.py` 82%. Unreadable folders, links and disk errors are untested. |
| Playback (`mpv.py`) | **79%** (100/127) | mpv detection (system / Flatpak / missing) is completely untested. |
| Server, settings, dev update (`server.py`, `settings.py`, `dev_update.py`) | **77%** (292/379) | `server.py` 70%: the whole play endpoint (lines 201-262) never runs in tests. `settings.py` 77%: almost no checks of bad settings. `dev_update.py` 93%. |
| UI (`ui/js`, `ui/css`) | not measurable | Two quick unit checks (colours, loading screen). Three thorough real-Firefox checks (`loading_screen_check.py`, `parsed_view_check.py`, `saved_library_check.py`) are **not** part of the normal test run. |
| Launcher and installer (`launch.sh`, `install-shortcut.sh`, `agent_guard.py`) | not measurable | `launch_cycles.py` and `dev_update_launch_check.py` are manual, outside the normal run. `agent_guard.py` has no tests at all. |

**Tests that would still pass if the feature broke:**
- **Timings:** the three timing tests only print a number. They would pass even if a scan took ten minutes.
- **Scan progress:** `test_progress_reaches_the_total` would pass even if progress never moved in between.
- **Failed save:** `test_a_failed_save_leaves_the_old_file_intact` only simulates failure at the final swap, not during writing.
- **Playback hint:** `test_failed_playback_hint_quotes_the_log` only checks that some hint exists, not that it's the right one.
- **Parser:** `test_never_raises` only checks that an answer comes back, not that it makes sense. Fixture cases check only the fields they list.
- **No-internet check:** `test_ui_loads_nothing_from_the_internet` misses addresses without a path after them, such as `https://x.com`, and `ws://` links.
- **No-raw-colours check:** `test_no_raw_colours_in_defaults` catches only hex colours, not `rgb()` or named colours, and doesn't look at `index.html`.
- **Safe Mode:** the Safe Mode check in `launch_cycles.py` only confirms the setting line is written. Headless Firefox never shows the prompt, so a typo in the setting's name would still pass.
- **Untested security checks:** nothing tests the server's Host-header and request-type checks. They could be deleted and every test would still pass.

**The five most valuable missing tests:**

1. **The card disappears during a rescan, and the saved library is kept** (H1). This guards the most serious bug found.
2. **The play endpoint, end to end with a fake mpv** (H2):
   - mpv fails to start in an unusual way, and the state goes back to idle.
   - Double play gets "already playing".
   - mpv missing gets the install message.
   - A path outside the folders is refused.
3. **Bad settings give a plain message** (H3, H4): null, wrong type and broken-text values, a missing file, and an mpv command with a bad quote.
4. **A held button does nothing twice** (H5): a browser check that a repeated A or B press doesn't open-and-play or back-and-quit.
5. **Three-digit anime numbers** (H7): `Show - 098.mkv`, `- 100`, `- 112` with no tag after. Add them as expected failures now, so the fix has a target.

Runner-up: tests for `agent_guard.py` (H9), which would have caught the `--output` gap.

## 4. Done well: keep as it is

- **Media safety.** Every write and delete in the app was traced. None can reach a media folder. The parser only ever reads names, and the server refuses any path outside the configured folders, including `..` tricks and links.
- **Atomic saving of the library.** It writes a temporary file, flushes it to the card, then swaps it in. A damaged or old-format file is ignored with one plain log line. A failed scan never replaces the saved library (apart from the H1 gap).
- **Resume is mpv's own.** The app doesn't reimplement playback. The small rewind script is careful, and the reasons are recorded in `docs/decisions.md`.
- **Playback doesn't block the app.** mpv runs in the background, a lock prevents double launches, and the mpv log is copied the same way for system and Flatpak mpv.
- **Server security basics.** It listens only on the device itself (127.0.0.1) and checks the Host header. Errors in the log name the kind of problem, never a file path.
- **One shared folder reader for Movies and TV.** It ignores `._` files, dot files and Sample folders, and is safe against link loops.
- **Known parser gaps are kept as tests**, listed in the spec, and all test names are invented.
- **The vendored packages:** pinned versions match `THIRD_PARTY_LICENSES.md`, all are used, all are pure Python, and a test proves the bundled copies are the ones loaded.
- **Fast UI.** 5,000 rows render within the 2-second loading minimum, and each arrow press takes about 2 ms.
  - Every name is inserted as plain text, so a filename can't inject anything into the page.
  - The focus ring and fill never depend on hover.
  - Colours all go through tokens, with contrast checked against accessibility guidelines (WCAG).
  - The wordmark font is bundled, and a test checks it hasn't changed.
- **Careful Firefox handling in `launch.sh`.**
  - A single-instance lock.
  - A graceful 15-second close.
  - Only the app's own Flatpak Firefox is stopped, never the user's browser.
  - It doesn't use `set -e` (an all-or-nothing error mode in shell scripts with surprising pitfalls).
- **The developer auto-update.** It is off unless explicitly turned on, only ever fast-forwards, skips on local changes or offline, and can't loop. Its tests use throwaway git repositories.
- **Licence headers.** Every source file outside `vendor/` has the GPL-3.0-or-later header.
- **No architecture assumptions.** No compiled code or x86-only paths anywhere. ARM risk comes only from speed (M1) and from tools that may be missing on Armada: `flock`, `pgrep` and `flatpak` (**to confirm**).
