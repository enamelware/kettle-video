# Spec — Milestone 2 (Walking Skeleton)

## Scope

The walking skeleton (milestone 2) scanned two configured folders (Movies, TV Shows) at launch and listed the files as plain text. Since the parsed library view and the saved library work the app works like this instead: on launch it loads the saved library and never scans; it scans the two folders only when asked (Rescan library or r), or once as part of the first launch, on the result screen (the first scan screen). Names are read from the file names: films are listed by title and year, TV shows by show, season and episode (see "Saved library" and "Parsed library view" below). Selecting a film or episode launches mpv fullscreen; when mpv exits, the app returns to the list, with the focus on the same row. The plain file list, grouped by subfolder, is now only a fallback (see "Fallback" under "Parsed library view"). Settings come from `settings.json` at the repo root. The app writes it in two cases only: onboarding saves the two folders chosen on first launch (the folder choice screens; see "Onboarding: choosing the folders"), and the Settings screen saves one kind's folder when it is changed there (the Settings screen work; see "Settings").

## API (see `backend/server.py` for the authoritative implementation)

- `GET /api/mpv-status` → `{"available": bool, "via"?: str, "install_hint"?: str, "problem"?: str, "hint"?: str}`. `problem` and `hint` come together when `mpv_command` is set but can't work (wrong type, a quote that isn't closed, or a program that can't be found; the settings mistakes work); the page shows both on the "mpv not found" screen. If this request fails or doesn't answer within 30 seconds, that screen says the app couldn't check whether mpv is ready.
- `POST /api/mpv-status/look-again` → the same answer, after reading `mpv_command` again from `settings.json` (the mpv missing screen; see "Onboarding: choosing the folders"). If the file can't be read just then, `{"available": false, "problem": "<its sentence>", "hint": "<the setting hint>"}`. The file is only read, in fresh start too. With the "pretend mpv isn't installed" option the answer stays "not installed".
- `GET /api/library` → `{"movies": ScanResult, "tv": ScanResult}` (rescans every call)
- `GET /api/library/parsed` → the saved library, ready to show (the parsed library view and the saved library work; see "Parsed library view" and "Saved library" below). Never scans. Developer only: `?fixture=N` (1 to 5,000) replaces the films with N invented ones (the Movies list work; see "Movies list").
- `POST /api/library/scan` → starts a scan of both folders in the background, or joins the one running: `{"started": bool, "state": "scanning", "files_done", "files_total", "last_result"}`. While mpv plays it answers `409` with `{"started": false, "busy": true, "error": "Rescan unavailable while playing"}` (the quick rescan and Remove work).
- `POST /api/library/remove-missing` → deletes everything marked missing from the saved library and saves it: `{"ok": true, "removed": int}`, or `{"ok": false, "error": "<sentence>"}` with the saved library unchanged (`409` during a scan). The only way anything leaves the saved library (the quick rescan and Remove work).
- `GET /api/library/scan/status` → `{"state": "idle"|"scanning", "files_done": int, "files_total": int, "last_result": null | {"ok": true, "message": "<what changed, e.g. 3 added, 1 missing, or No changes>"} | {"ok": false, "error": "<sentence>"}}` (`message` since the Home actions work, shown in the scan toast; never a path or a name)
- `GET /api/status` → `{"state": "idle"|"playing", "last_result": null | {"ok": bool, "error"?, "hint"?}}`. mpv's log location and its last lines stay in the backend (since the fresh start mode: they hold absolute paths, and the page never used them).
- `GET /api/continue` → the Continue watching carousel (the Continue watching work; see "Continue watching"): `{"items": [{"id", "kind": "movie"|"episode", "title", "label", "name", "caption", "position", "duration", "missing", "picture"}]}`, at most 6, newest first. Ids, words and numbers only, never a file location. `{"items": []}` when `resume` is off.
- `GET /api/continue/picture/<id>?v=<stamp>` → the tile's picture (`image/jpeg`), only for an item in the carousel; `404` otherwise.
- `POST /api/continue/remove {"id": "<id>"}` → `{"ok": true}` once the tile is out of the carousel (its picture deleted, its resume position kept), `{"ok": false}` if it wasn't there.
- `GET /api/onboarding/folders` → the folders with videos, grouped by place, for onboarding (the folder finder; see "Onboarding: finding the folders"): `{"places": [{"name", "kind": "internal"|"sd"|"usb"|"other", "state": "ok"|"not_ready"|"unreadable"|"partial", "folders": [{"id", "place", "name", "whole_place", "trail", "videos", "folders", "count_text", "examples", "problem"}]}], "checked": "<what was checked>", "looked": "<sentence for "No videos found yet", the No videos found screen>", "gaps": "<what the search couldn't see, shown above the list, the first onboarding review fixes>", "sd_card_found": bool, "browse": bool}`. Searches again on every call, and only reads. Ids, names and counts only, never a full path. `browse` says a folder dialog is there to open (the Browse somewhere else work). A folder's `problem` says why it can't be chosen, or is `null` (the first onboarding review fixes).
- `GET /api/onboarding` → `{"needed": bool}`: true when `settings.json` has neither folder set, so the first launch asks for them (the folder choice screens; see "Onboarding: choosing the folders"), and in fresh start until the folders are chosen (the fresh start onboarding work).
- `POST /api/onboarding/browse {"movies": "<id>"|null}` → opens the system's folder dialog and answers when it closes, with no time limit (the Browse somewhere else work; see "Onboarding: choosing the folders"). `{"ok": true, "picked": false}` for a cancel; `{"ok": true, "picked": true, "folder": {…as in /api/onboarding/folders…}, "place_kind": "<kind>", "message": "<sentence>"|null}` for a folder (`message` when it can't be read, holds Kettle's own files, or can't be used with that Movies folder); `{"ok": false, "message": "<sentence>"}` when no folder came back. Never a path in the answer or the log. `POST /api/onboarding/browse/close` closes an open dialog, which then counts as a cancel.
- `GET /api/onboarding/result` → what the result screen shows after the first scan (the first scan screen; see "Onboarding: the first scan and its result"), read from the saved library for the folders set now: `{"movies": {"set": false} | {"set": true, "path": "<place › folder>", "count"}, "tv": {"set": false} | {"set": true, "path", "shows", "episodes"}, "notes": ["<sentence>"], "nothing_found": bool, "failed": bool}`. `failed` when no folder set could be read. Never scans. A folder is its place and own name only, never a full path.
- `POST /api/onboarding/choose {"movies": "<id>"|null, "tv": "<id>"|null}` → ids from `/api/onboarding/folders` (any search this session), `null` for "I don't have …". `{"ok": true}` once both folders are saved in `settings.json` (in fresh start, the session's own, the fresh start onboarding work; the app uses them at once), or `{"ok": false, "message": "<sentence>"}` for a pair that can't be used, an id not found, or a save that failed (`settings.json` unchanged). `400` for a body that isn't that shape. Never a path in the answer or the log.
- `POST /api/play {"source": "movies"|"tv", "path": "<relative path>"}`, or `{"source": "movies", "id": "<film ID>"}` (the Movies list, the Movies list work: plays the film's first part that is there; an ID not in the saved library gives `400` `{"error": "file not found"}`), or `{"continue": "<id>"}` (a Continue watching tile, the Continue watching work: plays the part or episode it was stopped in; `400` `{"error": "file not found"}` if it isn't in the carousel) → starts mpv in the background and returns immediately: `{"started": true}`, or an error before it starts (`400` bad request, or `{"error": "Folder not available"}` when the source folder isn't there; `409` already playing, `503` mpv unavailable). The frontend polls `/api/status` to find out how it went — see the note on non-blocking playback below.
- `POST /api/shutdown` → `{"ok": true}`, then the backend process exits (after a playing film has closed; see "Starting and stopping")
- `GET /api/dev` → `{}` normally (the developer auto-update and its `dev_mode`, `status`, `build` and `note` went in the never-online work; see "Updates: never online by itself"). In fresh start it has `"fresh_start": true` (the fresh start mode; see "Fresh start for testing"); otherwise that key isn't there. With the size readout on it also has `"size_readout": true` (the sizing spike; see "Size readout"); otherwise that key isn't there.
- `POST /api/updates/check` (body `{}`) → the one check for updates, only when the viewer chooses Check for updates in Settings (the never-online work; see "Updates: never online by itself"): `{"state": "current" | "newer" | "error", "text": "<the row's words>", "last_checked": "Last checked: …", "development": bool}`, plus for a newer release `"version"`, `"notes"` (its release notes) and `"download_size"` (bytes, or `null`). `409` while a check runs.
- `POST /api/size-readout` with `{window_width, window_height, device_pixel_ratio, screen_width, screen_height}` → `{"ok": true, "logged": true}` the first time in a launch (one line in the launch log), `"logged": false` after that, 400 if a value isn't a plausible number (with one `size readout refused:` line in the log naming the field, never its value). Only there when the size readout is on; otherwise 404 (the sizing spike).

All requests must have `Host: 127.0.0.1:<port>` (rejected with `403` otherwise), and all `POST` bodies must declare `Content-Type: application/json` (also `403` otherwise) — basic hygiene for a loopback-only server.

**Non-blocking playback:** `POST /api/play` used to block for the whole film, which risks a request timeout in Firefox. It now validates the request synchronously (still returns `400`/`503` immediately for a bad request), then hands the actual mpv run to a background thread and returns right away. Only one playback runs at a time; a second `POST /api/play` while one is in flight gets `409`.

`ScanResult`:
```json
{
  "label": "Movies",
  "path": "/configured/root",
  "status": "ok" | "not_found",
  "reason": "does not exist" | "is not a folder" | "permission denied",
  "groups": [
    {"name": "Action", "files": [{"name": "Fernhollow Heist.mkv", "path": "Action/Fernhollow Heist.mkv"}]}
  ]
}
```
`reason` is only present when `status` is `"not_found"`. `path` is always the cleaned-up path the app actually used (see below), so it matches what's shown on screen.

**Settings paths are cleaned up on load:** `movies_path` and `tv_path` in `settings.json` have surrounding whitespace stripped, a `file://` prefix removed (with `%20`-style escapes decoded), and a leading `~` expanded to the home directory. This happens once in `backend/settings.py`; everything downstream (scanning, playback, error messages) sees only the cleaned path.

**Settings mistakes give one plain sentence** (the settings mistakes work). No settings file at all isn't a mistake: since the folder choice screens it counts as neither folder set, with every other setting at its default. A settings file that can't be read, isn't UTF-8 text (a UTF-8 file with the invisible start marker some editors add is fine), isn't valid JSON or doesn't hold its settings between `{` and `}`, and a `movies_path` or `tv_path` that is missing or not text (`null`, a number), each stop the backend with a sentence naming the setting, in the launch log. An empty `movies_path` or `tv_path` means that folder is not set (since the folder choice screens): with both empty the first launch asks for them (see "Onboarding: choosing the folders"), and a folder left empty is never scanned or played from. Only two things write `settings.json`: onboarding (both folders, on first launch) and the Settings screen (one kind's folder, the Settings screen work). `mpv_command` mistakes don't stop the app: they show on screen (see `/api/mpv-status` above), and `null`, `""` and `"auto"` all mean "find mpv".

Video extensions matched (case-insensitive): mp4, mkv, avi, mov, webm, m4v, wmv, flv, mpg, mpeg, ts, m2ts.

Settings also accept an optional `mpv_args` list (default `[]`) of extra flags passed straight to mpv, e.g. `["--hwdec=auto"]`, and an optional `keep_awake` (default `true`): hold the system's stay-awake lock while mpv runs (the keep-awake work) and, from the page, a Screen Wake Lock in Firefox for as long as the page shows "Playing…", because Steam's Gaming Mode timers ignore the system lock (the screen wake lock fix). **Keep-awake and sleep (the power button fix):** keep-awake only stops the screen dimming or turning off *by itself*; it never blocks a sleep the viewer asks for. The system lock asks for `idle` only (`systemd-inhibit --what=idle`), never `sleep`, so the power button and Steam's power menu always put the device to sleep, during a film, while paused, on Home and in the menu; during sleep mpv is frozen by the system with everything else, so on waking the film is at the same point (Kettle adds no pause of its own; that would need the live mpv connection planned for later), and if mpv was closed meanwhile, Resume brings it back as usual. The Screen Wake Lock and mpv's `--stop-screensaver=yes` only ever ask for "don't go idle" too. The play answer carries `keep_awake`; the page reports each change of its wake lock (`held`, `lost`, `refused`, `unsupported`, `released`) to `POST /api/wake-lock`, which writes one line to the launch log and refuses any other word. See the README, "Watching movies".

## Movie grouping (parser 4a, the movies parser work; used by the saved library since the saved library work)

`backend/library_movies.scan_movies(root)` turns the Movies folder into a list of movies. It is read-only. Try it with `python3 -m backend.library_movies "<path>"`.

- A folder that directly holds at least one video is a movie, or holds several movies. A folder with no videos of its own is only a container, and the scan goes inside it. A video loose in a folder is a movie too.
- Several videos in one folder are one movie with parts only when every one of them has a clear part marker (`Part 2`, `pt2`, `CD2`, `Disc 2`, or ` - 01` at the end) and they share a title and year. Parts are ordered by number and labelled "Part 1", "Part 2" and so on. A bare number (`Example Movie 2`) means a sequel, so it stays a separate movie.
- When a folder holds exactly one movie, the folder name gives the title and year. If the folder name has no year, the file's year is used. If the folder name gives no title, the file name is used. When a folder holds several movies, and for files loose in the root, each movie uses its own file name.
- Ignored silently: dot files and dot folders (including macOS `._` files), any folder named `Sample` (any case), and non-video files. Video means the extension list in `backend/scanner.py`.
- Links are followed only when they stay inside the root, and each real folder or file is counted once. Links leading outside are skipped and listed. A folder that cannot be read is skipped and listed, never a crash. A file or folder whose name can't be read as text (saved in another text encoding, common on old archives copied onto ext4 cards) is skipped and listed with "name can't be read", with each unreadable character shown as a replacement mark (�); it is never renamed (the unreadable name fix).
- Result: `MovieScan(movies, skipped)`. `movies` is sorted by title (ignoring case and accents), then year (no year first). Each `Movie` has `title`, `year` (or `None`), `parts` (a list of `Part(label, path)`, where `label` is `None` for a single file and `path` is relative to the root with `/`), and `flags` (from the name parser). `skipped` is a list of `Skipped(path, reason)`.
- Known limit: a genre folder holding just one movie looks exactly like that movie's own folder, so the movie takes the folder's name (for example "Comedy").

## TV grouping (parser 4b-1 and 4b-2, the TV parser work and the specials and odd names parser work; used by the saved library since the saved library work)

`backend/library_tv.scan_tv(root)` turns the TV Shows folder into shows, seasons and episodes. It is read-only. Try it with `python3 -m backend.library_tv "<path>"`; add `--episodes` to list every episode.

- A folder that directly holds at least one video, or holds season folders, is a show. A season folder is one whose whole name is a season marker: `Season 2`, `Season 02`, `S02`. Any other folder is a container, and the scan goes inside it. A folder named `Specials`, `Special` (any case), `Season 0` or `S00` is a specials folder and counts as a season folder. Other folders inside a show are scanned the same way as any folder, so an `Extras` folder becomes a show of its own.
- Videos loose in the root are grouped into shows by the title in their file names (ignoring case). The root itself is never a show.
- Show title and year come from the show folder's name. If it gives no title (for example a folder named just `Season 1`), the most common title among its files is used, with the most common year among those files.
- Season comes from the file name. If the file name has none, it comes from the season folder. If both exist and disagree, the file name wins and the episode is flagged `season-mismatch`. The exception is a specials folder: it always wins (season 0), because putting a file there is an explicit choice, and a file whose name says another season is flagged `season-mismatch`.
- Specials are season 0, labelled "Specials", and always listed last, after the normal seasons and after any "no season" group. A file named `S00E01` outside a specials folder goes there too.
- Seasons are sorted by number (10 after 9). Episodes without any season come after the numbered seasons. A show where no file has a season (absolute numbering, common for anime) is one flat list: a season with number `None`, followed by Specials if it has a specials folder.
- A multi-episode file (`S01E01E02`, `S01E01-E02`, `1x01-02`) is one entry with all its numbers.
- A file with no episode number is kept, flagged `unnumbered`, and listed after the numbered episodes of its season.
- Episodes are sorted by number, then by file name (ignoring case).
- Duplicates: files in the same season that share an episode number are all kept, all flagged `duplicate`, and listed in file-name order. No file is ever dropped. Unnumbered files are never duplicates.
- Accents: a decomposed accent (as macOS writes `é`, an `e` plus an accent mark) is joined into one letter (Unicode NFC) in show and episode titles, for display, grouping loose root files and sorting. Paths are never changed. Sorting ignores case and accents, so `É` sorts with the plain `E` titles; titles still display with their accents. It uses only Python's own Unicode data, not the device's language settings, so the order is the same on every device but isn't right for every language (German `ß`, Scandinavian letters).
- Names in any script (Japanese, Korean, Cyrillic) and names up to 255 characters are kept as they are.
- Ignore rules, links and unreadable folders: exactly as in "Movie grouping" (the same code).
- Result: `TvScan(shows, skipped)`. `shows` is sorted by title (ignoring case and accents), then year. Each `Show` has `title`, `year`, `seasons` (a list of `Season(number, episodes)`, where `label` gives "Season 2", "Specials" or "No season") and `path` (the show folder relative to the root, or `.` for loose root files). Each `Episode` has `numbers` (a list, empty when unnumbered), `number` (the first one, or `None`), `title` (the episode title from the name, if any), `path` and `flags`.
- Numbers in episode titles are kept: `11 - 511 Example Place` gives the title `511 Example Place`, and `Example Show - 03 - The 100 Doors` is episode 3 titled `The 100 Doors`, with no invented season, so it stays in a flat list. In a name that mixes spaces and dots (`Plain Example.S01E02`), the dot before the episode marker is a separator, so it joins `Plain Example S01E03`. A name made only of symbols (`@#$%^&()`) keeps every character.
- Three-digit anime numbers: a bare three-digit number after a dash is one absolute episode, with or without a tag after it: `Example Anime - 098`, `- 100`, `- 112` are episodes 98, 100 and 112 with no season, so they stay in one flat list. Without a dash, a packed number keeps its season and episode (`Show.Name.112.HDTV` is season 1, episode 12). Still open: four-digit numbers (`- 1012` reads as season 10, episode 12) and a three-digit episode number followed by a number in the title (`- 112 - The 100 Doors`).

## Parsed library view (the parsed library view)

First built as a temporary bridge so the parser's results can be checked on the device, in the real app. Since the saved library work it shows the saved library (see "Saved library" below); the library API (a later item) may still replace it. No new design: plain lists in the current look and the system font.

**Library:** two sections. Movies: one row per film (since the Movies list work: the title, the year in fog and "2 parts" on one line; see "Movies list"). TV Shows: one row per show (in the same order as films, ignoring a leading The, A or An, the title sorting work: "The Oakhollow" sits with the O shows; put in order again each time the page asks), with "3 seasons, 24 episodes" or "flat, 74 episodes" (no season folders) underneath, plus "1 special" when there are specials. Only rows take the focus.

**Episode list:** choosing a show replaces the library with its episodes: the show's title and counts at the top, season headings when there's more than one season (Season 1…, then "Episodes" for files with no season, then Specials). Each row: a label ("S02E05", "S01E01-E02", "73", "Special", or "?" when unnumbered), the episode title from the name (else the file name), and small muted notes for "unnumbered", "season differs from folder" and "duplicate".

**Keys:** A (Enter/Space) plays a film (**a film in several parts plays its first part only, for now**), opens a show, or plays an episode. B (q/Esc) goes back from the episode list to the library (focus on that show), and quits from the library as before. **d** shows or hides each row's original path inside its folder (hidden at start). **r** rescans, like the Rescan library row (see "Saved library"): "Rescanning…" shows while the current list stays on screen; afterwards the same show and row keep the focus if they still exist. After playing, the list isn't rescanned; the focus returns to the same row.

**Held buttons (the held button fix):** holding A or B counts as one press: the repeats a held key sends are ignored, so a held A on a show only opens it and a held B in the episode list only goes back. The arrows keep repeating, so a held D-pad still scrolls quickly. Check: `tests/held_key_check.py` (headless Firefox; not part of the unit tests).

**Mouse and touch (the click-then-Enter fix):** clicking or tapping a row only selects it (it doesn't play), except a film in the Movies list, which plays (the Movies list work); A then plays the selected row and the arrows move on from it. While the loading screen or "Playing…" is up, a click or tap changes nothing. Check: `tests/click_focus_check.py` (headless Firefox; not part of the unit tests).

**Loading:** see "Saved library": the app shows what was saved and never scans at launch.

## Saved library (the saved library work)

The app remembers the library between launches. **It never scans at launch**: it shows what was saved, and scans only when asked. Since the quick rescan and Remove work a rescan reads again only what changed, keeps files that have disappeared as **Missing**, and nothing leaves the library except through **Remove**.

**First launch** (nothing saved yet): onboarding's result screen scans the folders, with "Scanning… N of M", and says what it found (see "Onboarding: the first scan and its result", the first scan screen). The count is best effort and moves in two steps (films, then shows), because the grouping code reports no progress of its own. Until the first scan screen this was a temporary screen with one button, Scan my folders (`#first-scan`).

**With a saved library:** it shows at once. (Since the Home actions work Rescan library and Remove are rows of Home's menu, progress and the result show in a toast, and the Rescan row, its lines and "Rescanning…" are gone; see "Home actions". The rest of this section describes them as built in the saved library work and the quick rescan and Remove work.) A row at the top of the library, **Rescan library** (`.file-row.parsed-row[data-kind="rescan"]`, inside `.rescan-list`), has a muted "Last scanned just now / 5 minutes ago / 3 hours ago / yesterday / 2 days ago" line. A on it (or r anywhere) runs a full scan: the saved library stays on screen, the row's muted line shows "Scanning… N of M" and "Rescanning…" shows at the top, then the lists update and the focus stays where it was. At launch the first film (or show) has the focus, not the Rescan row. If a scan fails, the banner says "Couldn't scan the library. The saved library is unchanged."

**Folder not available** (SD card out, folder renamed): that section keeps its saved items, with a muted "Folder not available" under its title. Playing one shows "Folder not available". A rescan while it's away skips that section: its saved items stay exactly as they were and **nothing in it is marked missing**. The same goes for a Movies or TV Shows folder that is there but can't be listed (any read error, such as a half-mounted card), or that stops being listable part-way through the scan (card pulled mid-scan). A folder inside the section that can't be listed at any point of the scan keeps its items as they were. A section that has never been scanned, or whose folder path was changed by hand in `settings.json`, says "Not scanned yet" and shows no old items. A folder changed on the Settings screen (the Settings screen work) keeps the old folder's items, marked missing, until Remove N missing items clears them; whatever the rescan finds again in the new folder, at the same place inside it, is back as normal. A section skipped in onboarding (its folder left empty, the folder choice screens) says "No folder chosen", and rescans don't report it.

**Quick rescans (the quick rescan and Remove work):** before grouping, the scan lists every video (with the grouping's own folder rules) with its size and modified time, and compares them with the saved `files`. Names of new or changed files are read by the name reader; every other name (file and folder names alike) reuses the result saved in `names`, but only while the name reader is the same one that saved them: when the app is updated with a changed name reader (`backend/parser.py`, or the bundled guessit or rebulk version), the next rescan reads every name again once, so name reader fixes show up on their own. Grouping then runs again on everything, so the result is the same as a full scan. Progress stays "Scanning… N of M" (files found). On the real library on the Deck's card: full scan 1.2 s, quick rescan 0.01 s; 2,000 invented films: about 10 s full, 0.3 s quick.

**Missing (the quick rescan and Remove work):** a film, part or episode whose file is no longer found, while its folder is there, stays in the library with `"status": "missing"` and `"missing_since"` (UTC), keeps its ID and its place, and is still focusable. Its title is dimmed and a muted note says **"Missing"** (never dimming alone); a film with some parts gone says **"1 of 2 parts missing"** and plays its first part that is still there. A show is missing only when all its episodes are; episodes are marked one by one. A on a missing film, show or episode shows **"File not found. Rescan or remove it."** and doesn't start mpv. When the file comes back, the next rescan clears it. A renamed or moved file counts as a new one: the old entry shows as Missing next to the new one. Films and episodes inside a folder that can't be read are kept as they were, not marked missing.

**Remove (the quick rescan and Remove work):** while anything is missing, a second row sits under Rescan library: **"N missing items - Remove them"** (`.file-row.parsed-row[data-kind="remove-missing"]`). A whole missing film or show counts as one item; otherwise each missing part or episode counts as one. A on it opens the question **"Remove N missing items?"** over the list, an Enamel picker (since the picker confirm work; the list stays where it was, darkened behind it): **Yes, remove**, then **Cancel**, focused first, moved between with Up and Down; B is Cancel too. See "Design system: the remove question as an Enamel picker". Yes deletes the missing entries (empty seasons go with them) and saves with the same safe write; then the focus goes to the Rescan row. **A scan never removes anything by itself**, and there is no removing one item at a time.

**No rescans while playing (the quick rescan and Remove work):** while mpv plays, the Rescan row's muted line says **"Rescan unavailable while playing"**, r does nothing and the scan request answers busy; when mpv closes, the line goes back to "Last scanned …".

**Summary line (the quick rescan and Remove work):** after a scan, a second muted line under the Rescan row says **"Last scan: 4 new, 2 changed, 3 missing"**: new and changed files in this scan, and everything missing now. It is saved with the library, so it stays until the next scan (Remove sets its missing count to 0).

**The file:** `data/library.json` in the app folder (the `data_dir` setting can move it; a relative path is inside the app folder). Not in git (`.gitignore`). Deleting it brings back the first-launch screen. It lists file names, so it's never logged or uploaded; log lines name no paths.

```json
{
  "schema_version": 1,
  "generated_at": "2026-10-01T20:15:00+00:00",
  "sources": {
    "movies": {
      "root": "/configured/Movies",
      "last_scanned_at": "2026-10-01T20:15:00+00:00",
      "scan_seconds": 0.28,
      "counts": {"items": 3, "files": 4, "skipped": 0},
      "items": [{"id": "3f2a…", "key": "Title (2001)", "title": "Title", "year": 2001,
                 "parts": [{"label": null, "path": "Title (2001)/Title.2001.mkv"}], "flags": []}],
      "skipped": [{"path": "…", "reason": "cannot be read"}],
      "files": [{"path": "Title (2001)/Title.2001.mkv", "size": 1234, "mtime": 1700000000.0}]
    },
    "tv": {"…": "same, with shows: id, key, title, year, path, seasons [{number, episodes [{id, numbers, title, path, flags}]}]"}
  }
}
```

The items hold the grouping results, not display strings, so wording changes don't need a rescan. `files` (size and modified time of every file that is there) is what quick rescans compare against.

Since the quick rescan and Remove work (all optional, so a file saved before still loads; its first rescan reads every name once): films, parts, shows and episodes may have `"status": "missing"` and `"missing_since"`; each source has `names` (`{"movie:<name>" | "episode:<name>": the name reader's result}`), `names_version` (a short code for the name reader that read them; a different or absent one means none are reused) and `changes` (`{"new", "changed", "parsed"}` for its last scan); the file has `last_scan` (`{"new", "changed", "missing", "not_available": ["movies"…]}`).

**IDs:** the first 16 hex characters of the SHA-1 of `<source>:<key>`. The key is stored next to the ID: a film's folder (or its first file, when it shares the folder with other films or sits loose in the Movies folder); a show's folder (or its title, for loose files in the TV Shows folder); an episode's file. Renaming or moving a file gives a new ID.

**Rules:** saving writes a temporary file next to it and swaps it in, so a failed save leaves the old file as it was. A missing, unreadable, damaged or different-version file is ignored with one log line, and the app behaves as if nothing was saved. A source's saved items are used only while its saved folder path matches the settings. One scan at a time: a second request while one runs joins it. A scan error leaves the saved library unchanged. Each scan writes one line to the session log: `library scan saved: 3 movies (4 files) in 0.28 s, 0 skipped; 1 show (75 files) in 0.97 s, 0 skipped; 0 new, 0 changed, 0 missing, 0 names read`. Remove writes `library: removed 2 missing items`.

**Code:** `backend/library_index.py` (scan, save, load, IDs, missing items, Remove, the page's answer); the endpoints in `backend/server.py`. Checks: `tests/test_library_index.py` and `tests/test_library_rescan.py` (unit tests), `tests/saved_library_check.py` and `tests/missing_items_check.py` (drive the screens in a headless Firefox; not part of the unit tests).

**Snippet hooks (new, the quick rescan and Remove work):** a missing row has `data-status="missing"` (`.file-row.parsed-row[data-status="missing"]`), and its note is `.row-note[data-role="missing"]` (also used for "1 of 2 parts missing"). The Remove row is `.file-row.parsed-row[data-kind="remove-missing"]` in `.rescan-list`. The summary line is `.row-subtitle[data-role="summary"]` inside the Rescan row. The question is `#confirm-remove.confirm`, with `[data-role="question"]` and `[data-role="choices"]` holding `.file-row.parsed-row[data-kind="confirm-cancel"]` and `[data-kind="confirm-remove"]`. No existing hook changed.

## Updates: never online by itself (the never-online work)

**The rule:** Kettle Video never goes online by itself. Any request to the internet happens only when the viewer chooses an action that clearly says it will go online. Nothing goes online at launch, on a timer, on wake or in the background. Reasons in `docs/decisions.md` ("Never online by itself"). The public promise is the README's Privacy section (the bug report form work), audited against the code; `tests/test_privacy_statement.py` keeps the two in step.

**The developer auto-update (the developer auto-update) is gone.** `launch.sh` no longer runs an update step, `backend/dev_update.py`, its corner box ("Updated to …", "Already up to date", the build id) and `KETTLE_DEV_UPDATE` are removed. A `"dev_auto_update"` line left in a device's `settings.json` is simply ignored. Test devices now update only when asked (Pull the latest version, the Update and restart work, or `git pull` in Desktop Mode).

**The kiosk window's own traffic.** `launch.sh` writes these settings into the kiosk window's own Firefox profile at every launch (never the viewer's own Firefox), each group with a one-line comment: Firefox's update and add-on checks, usage and crash reports, studies, Safe Browsing lists, media plugin downloads (OpenH264, Widevine), connection checks, web push, location and region, search updates, link prefetching and other background downloads off. Two requests no setting stops (Remote Settings, Mozilla's background lists, and Google's media plugin check) are caught by a **dead end**: a proxy on this device at port 9, where nothing listens, for everything that isn't for the app's own server (which Firefox never sends through a proxy). `network.proxy.failover_direct` and `network.proxy.allow_bypass` are off, so Firefox can't go round the closed door (measured on Firefox 153: without them, Remote Settings went direct). The same profile also skips Firefox's Terms of Use notice on a new profile's first launch (`termsofuse.bypassNotification`) and the "restore your previous session" suggestion on a later launch (`browser.startup.couldRestoreSession.count` -1); Mozilla's own test runs use the same two settings.

**Check for updates** (Settings › About, a row under the version and licence notes):
- Under its label, "Last checked: never", then "today", "yesterday" or the date ("2 March 2026"). Kept on the device in the data folder (`update_check.json`) and changed only after a check that got an answer; showing it never goes online.
- **A** sends one request. While it runs the row reads "Checking…" and nothing else waits for it: the controller still moves, Settings can be left and opened again. The server gives up after 10 seconds and never retries by itself; one check at a time.
- **A release install** (and any copy that isn't a git checkout) asks GitHub's release information for this app's repo for the latest release (`https://api.github.com/repos/enamelware/kettle-video/releases/latest`), with the standard library's own web client: no cookies, no identifiers, nothing about the viewer, the device or the library, and a plain user agent `Kettle-Video/<version>`. GitHub sees the device's IP address and the app's version, nothing else.
- **Results**, in the row under Last checked: "Up to date (v1.0.0)", or "Version 1.1.0 is available" with a **What's new** row under it (its meta "Version 1.1.0"). A on What's new shows the release notes from the same answer (nothing else is fetched) in the licence's reading view: a list item or a heading is a paragraph of its own; Up and Down scroll; B goes back to the row. On an installed copy, **Update and restart** follows under What's new (the Update and restart work, see "Update and restart" below), its meta the download size from the same answer ("About 40 MB").
- **Errors**, in plain words: "Couldn't check: no connection" (the name can't be looked up or there is no network); "Couldn't check right now. Try again later." (GitHub unreachable or slow, rate-limited, the repo not public yet, or an answer that isn't release information).
- **A development install** (a git checkout without the installer's mark: the development devices) compares with its remote's main branch instead (`git ls-remote`, which changes nothing in the copy): "Up to date (v0.1.0-dev, abc1234)" when main is this commit or behind it, else "A newer version is on main (def5678)", with no What's new row; when newer, a **Pull the latest version** row follows (the Update and restart work, see below). Release installs never do this.
- **The launch log** gets one line per check: `update check: latest release: newer` (or `main: current`, or `couldn't check (<why, in a few words>)`). Nothing about the device.

**Checks:** `tests/test_updates.py` (the network replaced throughout by fakes that fail the test if touched: nothing at launch, while the app is used or after a while; only the Settings action checks, and a GET never does; the exact request, against a stand-in GitHub on the device; the time limit and no retry; every result and error; the download size from the answer; the development check against a local git remote, changing nothing; Last checked only after an answer, and after a restart; the page asking from one place only; the launcher's dead end and prompt settings), `tests/updates_check.py` (the rows, Checking…, the results and What's new at every window width, controller only, in a Firefox with the kiosk profile's settings) and `tests/kiosk_profile_check.py` (the kiosk profile from `launch.sh`, started and closed as the launcher does, twice: no connection from the window to anything but the device in the first 30 seconds, nothing a setting switches off even tried, no Terms of Use notice, bar or dialog on either launch).

### Update and restart, and Pull the latest version (the Update and restart work)

Both come after Check for updates found something newer, start only from A on their row and a yes, and are the only other requests the app makes online: each follows the viewer's clear choice. `backend/app_update.py` does the work; the page follows it.

- **The row.** On an installed copy where the installer put it (it has the installer's mark, and `~/.local/share/kettle-video/app` leads to it), when the release has both its archive and its `.sha256` file at this app's own release address (`https://github.com/enamelware/kettle-video/releases/download/…`): **Update and restart** under What's new, with the download size ("About 40 MB", "Less than 1 MB"). Otherwise it isn't offered and running the installer again stays the way (README). On a development copy, when main is newer: **Pull the latest version** under Check for updates. Release installs never show it.
- **The question:** Enamel's picker confirm, "Update to 1.1.0? Kettle Video will restart." (or "Pull the latest version? Kettle Video will restart."), then Update and restart (or Pull and restart), then Cancel, focused first; B and Cancel change nothing.
- **While it runs**, Enamel's toast says how far it has got: "Downloading 1.1.0… 40%", then "Installing…" (or "Pulling the latest version…"), then "Restarting…". Everything waits for it but B, which is **Cancel** while it downloads (the hint bar says B Cancel); from Installing on, nothing stops it and the hint bar has no B. No update starts while a film plays (the server refuses: "Not while a film is playing."), and no film starts while one runs.
- **The download:** the archive, then its checksum file, from the addresses in the check's own answer (kept by the server, never sent to the page), with the standard library's web client, no cookies, and the same plain user agent as the check (`Kettle-Video/<version>`); nothing about the viewer, the device or the library. Into a temporary `.download-…` folder beside the app folder (never the data folder), deleted afterwards; a leftover from a power cut goes with the next update. 30 seconds without data gives up.
- **The install** is the installer's shared step, `installer/update.py` (the installer's update step), from this copy's own folder: it checks the checksum, places the new version, checks it starts cleanly, removes the previous one, and rolls back on any failure. There is no second checksum check or rollback in the app. It never opens the data folder or the settings file; an older version is never installed from here.
- **Restart in place:** the server stops as for Quit (a playing film is impossible here; a fresh-start folder is deleted), then the same process becomes the new version's server (`python3 -u -m backend.server` from the new folder, on the same port). `launch.sh` and Steam watch that process, so the app never looks closed and Gaming Mode doesn't drop back to the library; `launch.sh` is not changed, and a new version's own `launch.sh` takes effect at the next launch. The page waits until a server with a new id answers, then loads again, opening on Home as at any launch, with the toast "Updated to 1.1.0" (the message reaches the new server once, through `KETTLE_UPDATE_NOTE`, and is given to the page once).
- **When it doesn't work:** a failed download: "Couldn't download 1.1.0: no connection. Nothing was changed." or "Couldn't download 1.1.0 right now. Nothing was changed. Try again later."; Cancel: "Update cancelled. Nothing was changed."; a damaged download: "The download of 1.1.0 was damaged, so nothing was changed. Try again later."; a failed install or first start: rolled back by the shared step, then the previous version restarts in place, saying "The update to 1.1.0 didn't work, so 1.0.0 was put back as it was."; anything else stopped before a change: "Couldn't update to 1.1.0, so nothing was changed. Try again later." Each step is a line in the launch log, starting `update:`.
- **Pull the latest version** (development copies): only on `main`, only with no changes to tracked files (untracked ones such as `settings.json`, `data/` and `logs/` don't count), checked again just before; `git fetch` of the remote's main (with no password or host-key question), then a fast-forward only. Refusals change nothing: "Not pulled: this copy has changes of its own. Nothing was changed.", "Not pulled: this copy isn't on main. Nothing was changed.", "Not pulled: this copy has moved away from main. Nothing was changed.", "Couldn't pull: no connection. Nothing was changed.", "Couldn't pull right now. Nothing was changed. Try again later."; nothing new: "Already up to date (abc1234)", no restart. Then the same restart in place, with "Updated to the latest version (def5678)".
- **API:** `POST /api/updates/check` also answers `"can_update": true` and `"download_text"` (a newer release that can be installed from here) or `"can_pull": true` (a newer main on a development copy). `POST /api/updates/install {"version"}` and `POST /api/updates/pull {}` → `{"ok": true, "boot", "state", "text"}` once started, or `409` `{"ok": false, "text"}` (before a check, another version, a film playing, one already running, a copy that can't update itself). `POST /api/updates/cancel {}` → `{"ok": bool}` (only while downloading). `GET /api/updates/status` → `{"state": "idle" | "downloading" | "installing" | "pulling" | "restarting" | "failed" | "cancelled", "text", "boot"}` (`boot` is the server's own id; it changes after the restart). `POST /api/updates/note {}` → `{"note": "Updated to 1.1.0" | null}`, given once after a restart. `POST /api/play` → `409` `{"error": "updating"}` while an update runs.
- **Checks:** `tests/test_app_update.py` (stand-ins only, nothing online: invented installed copies in a temporary home updated by the real shared step; a checksum mismatch, a failed download, a failed install or first start rolled back and restarted, Cancel, playback both ways, one at a time, the data folder byte for byte, no second checksum or rollback code, the real download against a stand-in on the device, the pull against local git folders, the server's answers and the note), `tests/test_restart_in_place.py` (the real `launch.sh` on an installed copy of this app in a temporary home, with a stand-in window: the launcher and the server stay the same processes, the server comes back from the new version's folder, the page loads again with the note; a version that can't start is rolled back and the previous one restarts) and `tests/app_update_check.py` (the row, the confirm and the toasts at every window width, Cancel, Installing…, the reload with "Updated to 1.1.0", and the development row's confirm and refusal, controller only).

## Movies list (the Movies list work)

The Movies tab is a fast list to scan at a glance, still smooth at 2,000 films. The TV Shows tab, the Rescan row and the Remove row are unchanged.

**Each row:** the title, then the year in fog, then labels in words, never colour alone: "2 parts" for a film split into several files, and "Missing" or "1 of 2 parts missing" (the quick rescan and Remove work). A long title wraps to two lines at most and ends with "…"; the focused row shows the whole title. On the focused row all text is snow, as on every row (since the third design system step: the title is strong white and the year and labels soft grey, Enamel's row style). When a row grows or shrinks as the focus moves, the newly focused row stays where it was on screen, so the list doesn't jump. The page splits the year off the end of `display_title` ("Title (2001)"), where the back end always puts it.

**Order and letter groups** (worked out by the back end, `backend/library_order.py`): every film has a letter group: `#` for a title that starts with a number or a symbol, `A` to `Z` (an accented letter counts as its plain letter: "Émile" is under E; so do Latin letters such as Ø, Ł, Æ, Đ, ß, Œ and Þ, which count as O, L, A, D, S, O and T, for the group and for the order inside it: "Ørsted" is under O, "Łódź" under L), or `other` for a title in another alphabet (shown as "…"). The list runs #, A to Z, then other. Inside a group: by title, ignoring capitals and accents ("Émile" sits with "emile"), then by year (no year first), then by the film's ID, so the order never shuffles. **A leading "The", "A" or "An" is ignored** for the order and the group (the title sorting work): "The Mossbrook" is under M, "A Burrow's Tale" under B, "An Emberfall" under E, "The 37 Lanterns" under #. Only one article, once, and only when a space and then a letter or digit follow: "The", "A", "The The", "A.B. Example Machine", "Thelwick" and "Theatre of Example" stay under their own first letter. English only (no Le, La, Die…). The title shown never changes. Equal titles go by the full title with its article ("The Thistlecombe" before "Thistlecombe"), then year, then ID. The answer gives each film `sort_index` and `letter` (see "Parsed library view").

**Controller and touch:**
- A plays the focused film straight away. The page asks for it by its ID (`POST /api/play` with `"id"`), never by its location.
- Inside the list, Right jumps to the first film of the next letter that has films, Left to the first film of the previous one. Empty letters are skipped. No wrapping round: Left in the first group and Right in the last do nothing. From the Rescan or Remove row, Right goes to the first letter and Left does nothing. On the "Remove N missing items?" question Left and Right do nothing, so a stray press never lands on Yes, remove.
- On the tab strip, Left and Right still switch tabs. Up and Down move one row; Up from the first row goes back to the tabs.
- A letter strip down the right edge lists only the letters that have films, with the current one (the focused film's) in bold with a bar beside it. It is for touch only: tapping a letter jumps there; it never takes the focus. The list keeps room for it, so it never covers a row. Since the letter strip fix it is drawn in front of the tab strip, and when every letter can't fit at a readable size it scrolls by touch, the app keeping the current letter in view.
- Tapping a film plays it. When a film ends, the focus comes back to the same row.

**Speed:** every row is drawn (no drawing only the visible rows; see `docs/decisions.md`). The developer console shows how long the list took to draw ("Movies list: 2000 rows drawn in … ms") and each letter jump ("Movies list: jump: to M in … ms"); both are also kept as standard performance measures ("Movies list: draw", "Movies list: jump"). Measured on the Steam Deck (headless Firefox, 2,000 invented films): about 120 ms to draw at both window sizes checked then, well under the 300 ms limit; a letter jump takes 2 to 4 ms (under 25 ms to the next frame). Re-measured for the title sorting work, with a third of the invented titles starting with The, A or An: about 120 ms to draw at both sizes, letter jumps 2 to 3 ms (under 20 ms to the next frame).

**2,000-film switch (developer only):** add `?fixture=2000` to the page address (any number from 1 to 5,000) to see that many invented films instead of the saved ones, always the same for the same number, with long titles, accents, numbers, symbols, other alphabets, some films in two parts and a few missing. Off unless asked for. Invented films can't play (they aren't in the saved library: "file not found").

## Home and Continue watching (the Continue watching work)

**Home** is the library page: the top bar, the Continue watching carousel, the tab strip with the Movies and TV Shows lists, and the hint bar. The carousel shows only above the library lists: not inside a show's episodes, on the "Remove N missing items?" question, the first-launch screen or the plain-list fallback. With nothing to show it disappears completely (no heading, no gap).

**What goes in and what leaves** (worked out by the back end, `backend/continue_watching.py`; kept in `<data_dir>/continue.json`):
- When B (or Esc) quits mpv, a small mpv script shipped with Kettle (`backend/mpv_scripts/quit_capture.lua`, option 1 of the spike in `docs/spikes/mpv-quit.md`) pauses, saves the frame on screen (video only, no subtitles or on-screen text), writes the position and length, then quits as mpv's own q does, so mpv's resume save and the 5-second rewind are unchanged. mpv writes into a fresh folder under `/tmp` (the Flatpak mpv can't write into the app's folder); the app moves the files after mpv has closed. Playing to the end writes "finished". Any other way of closing (the window closed, the app closing, a stop signal such as Steam's "Exit game") writes the position and the frame too, taken just before mpv lets go of the film (the server shutdown check); only a forced kill saves nothing. The script is used only for files of the saved library, and only with `resume` on.
- An item shows once it has been stopped at 60 seconds or later, and leaves once it is **finished**: 95% watched, or played to the end. Resume has no "finished" rule of its own (mpv only knows the very end), so this rule is Kettle's (`docs/decisions.md`). A finished item's picture is deleted.
- At most 6 tiles, the most recently stopped first. When a seventh arrives, the oldest drops off (its picture is deleted). It comes back only the next time it is stopped.
- A film in several parts gets one tile; its progress and caption are for the part being watched, and the caption adds "Part 2". A show gets one tile, for the episode stopped most recently, named "Show name · S2 E5", "Show name · Episode 37" for a show numbered straight through, or "Show name · Special 3" for season 0. No "next episode" logic.
- **Remove:** X (Backspace) on the focused tile removes it at once, with no question. Its picture is deleted. The resume position is kept (it is mpv's): the film still resumes from the list, and it comes back the next time it is played and stopped. The focus moves to the next tile, or the previous one if it was the last, or to the tabs if the carousel is now empty.
- **Missing files:** a tile whose file is marked missing in the saved library, or whose folder isn't there right now (card out), keeps its place and progress bar; its frame turns dark and grey with "Missing" in the top-left corner, and the large tile's caption reads "Title · Missing · stopped at 0:38:10". A on it does what A does on a missing row: "File not found. Rescan or remove it." Once the file is back, the tile goes back to normal. Confirming Remove missing items also removes their tiles and pictures.
- Nothing here touches mpv's saved positions: finishing, removing or dropping off never loses one.

**Layout:** the carousel sits above the tabs, under a "Continue watching" heading. The first tile is large, with a caption underneath: "Title · Resume at 1:12:40 · 44 min left" (times read h:mm:ss, or m:ss under an hour; minutes left round up; under a minute: "less than 1 min left"). The other tiles are smaller, beside it, with only the name underneath (two lines at most). Tiles are 16:9, the frame cropped to fill; a tile with no picture is a plain surface with the name on it. Every tile has a progress bar along its bottom edge; the focused one has the focus ring and its caption turns white (since the third design system step these are Enamel's: a plain frame with the name in small capitals, a thin accent progress bar and the accent ring; see "Design system: lists and Continue watching"). Since the responsive layout work the tile sizes are Enamel's, taken from the width the row gets, so a wider row shows more tiles (see "Responsive layout"). Like Steam's Recent games row, all tiles stand on one shared bottom edge, so the large tile rises above the small ones and every progress bar sits on the same line; the large tile's caption and the small tiles' names start together on the line under the row, the caption at the large tile's left edge (the tile alignment work). The row scrolls sideways and keeps the focused tile in view; it leaves room for the Movies list's letter strip. A film's title is shown without its year.

**Controller and touch:**
- At launch the focus starts on the first tile when the carousel shows; otherwise on the selected tab, as before.
- Left and Right move between tiles and stop at the ends (never a letter jump). Down goes to the tabs; Up from the tabs goes back to the tile focused last. A resumes at once (`POST /api/play` with `"continue"`, by the tile's ID). B quits, as everywhere on Home.
- While a tile has the focus, the hint bar shows **(A) Resume** and **(X) Remove** (and B). By touch, a tap resumes and a swipe scrolls the row; there is no remove by touch.
- When mpv closes, the carousel is read again. A film started from a tile: the item just watched comes first and has the focus; if it finished and left, the focus goes to the first tile, or to the tabs if the carousel is empty. A film started from a list row: the focus goes back to that row, as before (`docs/decisions.md`). After a rescan the carousel is read again too, and the focus stays on the carousel if it was there.
- The controller's X sends Backspace (`docs/device-setup.md`). Held, it counts as one press, like A and B.

**Pictures:** one JPEG per tile, about 480 px wide, named after the item's ID, in `<data_dir>/thumbnails/` (`data/thumbnails/` by default, excluded from git like the rest of `data/`). Never inside a media folder: if `data_dir` is set inside one, no pictures are saved or deleted there and the tiles show plain surfaces. The full-size frame is shown first, then replaced in the background by the small picture, which mpv makes from it after it has closed (about 0.4 s with the Flatpak), so the return to the list is never slowed. A picture is replaced each time the item is stopped, and deleted when it finishes, is removed with X, drops off, or is removed from the library; at launch, any picture that no longer belongs to a tile is deleted. The page fetches each picture by ID (`GET /api/continue/picture/<id>`); file locations never reach the page, and picture names and contents never go into the logs (mpv's own screenshot messages are left out of the mpv log).

**Speed:** the carousel is asked for alongside the library and the pictures load once the tiles are on the page, so they never hold up Home. The developer console shows "Continue watching: draw" and "Home: ready" (from the page opening), and the session log "continue watching: stop saved in … ms" after each stop (timings in the issue).

**Snippet hooks (new):** `#continue-watching.continue-watching` now holds `.continue-heading` ("Continue watching") and `.continue-row[data-role="tiles"]`, with one `.continue-tile` per item. A tile has `data-id`, `data-kind="movie" | "episode"`, `data-size="large" | "small"`, `data-picture` when it has a picture and `data-status="missing"` when its file is missing. Inside: `.continue-frame` holding `.continue-picture` (the `img`), `.continue-surface-name` (the name on a plain surface), `.continue-missing[data-role="missing"]` ("Missing") and `.continue-progress` with `.continue-progress-fill` (its width is the custom property `--progress`, 0 to 1); then `.continue-caption`. In the hint bar: `[data-role="select"]` (the Select/Resume word) and `.hint[data-role="remove"]` (X Remove, `hidden` off a tile). New tokens: `--continue-tile-height`, `--continue-small-tile-height`, `--continue-progress-height`, `--continue-missing-filter`, `--continue-ring-room` (all but `--continue-missing-filter` since removed: `--continue-progress-height` in the third design system step, the others in the responsive layout work). No existing hook changed.

**Code:** `backend/continue_watching.py` (rules, the saved list and the pictures), `backend/mpv_scripts/quit_capture.lua` (the quit script), `backend/mpv.py` (`build_command`'s `capture_dir`, `shrink_frame`), `backend/server.py` (`/api/continue…`, saving each stop), the page in `ui/js/app.js` and `ui/js/keyboard.js`. ## Starting and stopping (the server shutdown check)

`launch.sh` starts the server, then the app's Firefox window, and waits until one of them is gone; then it stops the other. Only one copy runs at a time: a second start while the app is open is turned away and the first keeps working (the start-up fix). Results of every way of closing, by device: the server shutdown check.

**When the app closes while a film plays** (option A, `docs/decisions.md`): before the server stops, whatever stopped it (a stop signal from the launcher or from Steam's "Exit game", or `POST /api/shutdown`), it asks mpv to quit normally, as B does, through mpv's control socket (`--input-ipc-server`, in a fresh folder under `/tmp`, removed when mpv closes; a socket the user set in `mpv_args` wins, and then the app can't ask). mpv saves its resume position, and the Continue watching script its position and frame (see "Home and Continue watching"). The server waits at most 2 seconds for mpv to close and the stop to be kept, then goes anyway. The full-size frame stays as the tile's picture: there is no time to make the small one. mpv getting the stop signal itself (Steam's "Exit game" can send it to every process) gives the same result. Nothing changes in `launch.sh`.

**Not covered:** if the launcher itself is killed (a crash), the server and the Firefox window stay, and Kettle doesn't start again until they are closed (the designer's choice, the server shutdown check).

**Code and checks:** `backend/server.py` (`close_server`, `finish_playback`), `backend/mpv.py` (`build_command`'s `control_socket`, `ask_to_quit`), `backend/mpv_scripts/quit_capture.lua` (the closing hook). `tests/test_close_while_playing.py` (unit tests, fake mpv), `tests/continue_watching_mpv_check.py` (the real mpv, stop signal and the app's quit request) and `spikes/kiosk-quit/quit_check.py` (every way of closing the real app, with what is left behind, whether the position and the picture were kept).

## Playback controls (the playback controls work)

While a film plays, a few buttons do the obvious things and nothing else does anything. Everything is given to mpv at each launch (`backend/mpv.py`, `PLAYBACK_OPTIONS`); Kettle never writes to mpv's own settings folder.

- **mpv's built-in control bar is off** (`--osc=no`). There are no on-screen buttons.
- **Every default mpv key is off** (`--input-default-bindings=no`), and Kettle's key file `backend/mpv_input.conf` is the only list of keys (`--input-conf`). The designer's own `input.conf` is not read then.
- **The wording** comes from a small script of Kettle's, `backend/mpv_scripts/playback_controls.lua`, passed at every launch. It binds no keys itself; the key file calls its actions by name. No third-party script.

**Buttons**, by the label on the device (Steam's button names, which follow position: A is the bottom face button), and the key Kettle's Steam layout sends:

| Button | Key | Does |
| --- | --- | --- |
| A | Space | Play or pause |
| B | q | Stop and go back to Kettle, saving the position (and the Continue watching frame) |
| D-pad Left / Right, left stick left / right | Left / Right arrow | Back / forward 10 seconds |
| L1 / R1 | j / l | Back / forward 1 minute |
| X | Backspace | Next subtitle track, ending on Off, then the first again |
| Y | a | Next audio track (never Off) |
| D-pad Up | Up arrow | Show where I am |
| D-pad Down | Down arrow | Nothing |
| Start | m | Nothing (in the Kettle list it opens the menu, the Home actions work) |
| L2, R2, right stick, Select | none | Nothing |
| Volume | (the device's own) | The device's own volume; Kettle maps none |

The keys are what Steam Input must send (`docs/device-setup.md`). In the Kettle list the same buttons keep their list meaning (X is still Remove on a Continue watching tile); they only change meaning inside mpv. j, l and a do nothing in the list.

**Keyboard** (Desktop Mode testing): Space, Left, Right and Esc do the same as A, D-pad Left, D-pad Right and B. Every other key does nothing while a film plays, including mpv's usual ones: f (fullscreen), s (screenshot), m (mute), 9 / 0 and the mouse wheel (volume), Enter and < > (next / previous file), i (statistics), o (progress), ` (console), the right mouse button (menu) and the keyboard's media keys.

**Touch:** one tap anywhere plays or pauses. A second quick tap is a second tap, never a double click (mpv's default double click is fullscreen; it is off).

**Feedback**, with mpv's own on-screen text and progress bar:

- Seeking: the progress bar with elapsed and total time, for 2 seconds.
- Pausing: "Paused" with elapsed and total time, for 3 seconds. Playing again clears it.
- D-pad Up: the title, elapsed and total time and the progress bar, for 3 seconds. The title is Kettle's own, with the year as in the Movies list and the part or episode as on the Continue watching tiles: "Title (Year)" for a film, "Title (Year) · Part 2" for one part of a split film, "Show · S2 E5" (or "Episode 37", "Special 3") for an episode. Kettle passes it to mpv at launch (`--force-media-title`). A file outside the saved library (the plain-list fallback) shows what mpv finds itself: the title stored inside the file, else its file name.
- X: "Subtitles: English", …, then "Subtitles: Off". With no subtitle track: "No subtitles in this file".
- Y: "Audio: Japanese". With a single track: "Only one audio track"; with none: "No audio in this file".
- A track's name is its language in English (common two- and three-letter codes; any other code is shown as it is), else its title, else "Track 2" (its number).
- Text: the system font (`sans-serif`), white with a black outline (2.5), size 40. mpv scales this to the screen height: about 5.5% of it, whatever the screen.

**Must keep working:** B and Esc still go through the Continue watching script (`quit_capture.lua`), which now takes q and Esc with forced bindings, so switching the default keys off doesn't switch it off; without that script (resume off, a file outside the library) the key file quits plainly. Resume and its 5-second rewind, keep-awake, the focus coming back to the same row, and multi-part films play as before.

**The designer's own mpv settings:** mpv still reads its `mpv.conf` (on this Deck there is one, in the Flatpak's config folder) and loads any scripts in its `scripts` folder. Kettle's options on the command line win over the same options in `mpv.conf`, so it can't bring the bar back or change the text style, but a script of the designer's (for example a third-party control bar) would still load and could add its own bar or keys. `mpv_args` in `settings.json` still wins over everything above. Not decided: reported on the playback controls work.

**Code and checks:** `backend/mpv.py` (`PLAYBACK_OPTIONS`, `KEY_FILE`, `build_command`), `backend/mpv_input.conf`, `backend/mpv_scripts/playback_controls.lua`, `backend/mpv_scripts/quit_capture.lua`. `tests/test_playback_controls.py` (unit tests: the launch options, the key file against the button table) and `tests/playback_controls_mpv_check.py` (every key with the real mpv on two test clips, no window; not part of the unit tests).

### Units and grid audit

Every size in the app's own CSS (`ui/css/`) answers one question: should it grow when the viewer makes text bigger? Yes is rem, no is px (lines, corners, shadows, room for a ring or a lift, side padding that would squeeze text). Each is a multiple of 4 in its own unit (0.25rem or 4px). Anything that holds text uses a minimum height, rem widths never pass their space, the one breakpoint is in rem, and nothing sets the root font size. `tests/test_no_fixed_pixels.py` checks the grid in px and rem, the root font size and fixed heights; `tests/text_size_check.py` checks every screen with Firefox's text size at 200%.

Fixed in the Enamel 0.11.0 upgrade:
- The room kept around a focused button (Look again, the onboarding buttons): `var(--en-space-tight)` to `var(--en-lift)`, the height it rises.
- The episode label's column: `min-width: 4.5em` to `min(4.5em, 100%)`, so it never passes its row.
- The letter strip: `max-width: 100%` with its rem width.

Exceptions, each with its reason:
- **The error messages' red bar** (`var(--en-space-tight)`, rem) and **the tab strip's gap and side padding** (`var(--en-space-gap)`, rem): by the rule they should be px (a line; room for a ring; side padding that would squeeze the tabs), but every app size must come from an Enamel token and Enamel has no px token for these. They stay on their tokens; asked of Enamel on the Enamel 0.11.0 upgrade (`needs enamel`). At 200% text they grow, and every screen still passes.
- **The wordmark's size** (`clamp(2.5rem, 11vw, 6rem)`): sized by the window's width so KETTLE stays on one line (the Brand v0.1 work); its rem limits are on the grid.
- **The letter strip's letter size** (a formula from the room between the bars, divided among the letters, between 0.7 of and the small text size), and its letters' **2.4em / 1.2em** touch heights: text sizes and ratios of the letter's own size.
- **The episode label's 4.5em:** a ratio of its own text, so it grows with it.
- **Letter spacing** (`0.3em`) and the developer box's room (`2 × 1.5 × small text`): ratios.
- **The hidden heading's 1px box:** the screen-reader-only pattern, not a size anyone sees.
- **A picture's `height: 100%`:** fills its frame; it holds no text.
- **Side padding in rem** on the error messages and the "Missing" label: kept, as Enamel's own rows and badges keep theirs in rem.
- **Sizes the app measures** (`--shell-bar-height`, `--tab-strip-height`, set in px by the app from the real bars): measurements, not choices. (`--shell-bar-height` went in the Home polish with the docked bar.)
- **Text size 200% in windows smaller than Enamel's smallest supported box** (20rem by 15rem, so 640 by 480 at 200%): Enamel only asks that the page scrolls there. At 320 by 240 with 200% text (10rem by 7.5rem) the wordmark and some messages run past the edge. No device is that small at that text size.
- **A faint 1px line** under the current letter of the letter strip, at 200% text in a short window: Firefox drawing the letter's 4px side bar on a box that ends part-way through a pixel. Older than the Enamel 0.11.0 upgrade, not from Enamel; left as it is.

## Responsive layout (the responsive layout work)

No layout is tied to a screen size, a device or an aspect ratio: every screen adapts to the space it gets, from Enamel's smallest supported box (20rem wide by 15rem tall, 320 by 240 at the browser's normal font size) to very wide. Below that the page scrolls; nothing overlaps or is cut off. The Steam Deck and the Nova are where it's tested, not what it's designed for. Reasons in `docs/decisions.md`.

- **Continue watching:** the tiles take Enamel's widths from the width the row gets (the row is Enamel's shelf, a size container): a small tile is two fifths of the row, between 10rem and 16rem; the large one three quarters, between 12rem and 28.25rem (28rem before Enamel 0.8.0). A wider row shows more tiles, and the row scrolls sideways when they don't all fit. The ring room around the tiles is Enamel's `--en-c-shelf-room`. The tile alignment work's layout stays: frames on one bottom edge, captions on the line below.
- **Lists, tabs and the hint bar** are Enamel's: rows grow when a title wraps, tabs and hints wrap onto another line when they don't fit, and the page keeps room for the hint bar at its real height. The tab strip is one line of tabs tall at least, and the app keeps `--tab-strip-height` at its real height when the tabs wrap.
- **Short windows:** where the window can't keep the top bar, two lines of tabs and the hint bar pinned with two rows between them (under about 24.25rem tall since Enamel 0.8.0, the Enamel 0.8.0 upgrade; since the Home polish, with no docked bar, under about 20rem and only the tabs), the top bar and the tabs scroll with the page, so a row moved to always has room. In Enamel's smallest box one whole row is kept in view rather than two, since a film title wraps there (the Enamel 0.8.0 upgrade). A focused row taller than the room (a long title in a very short window) shows its top.
- **Up and Down scroll a message:** on a screen with nothing to focus ("mpv not found" and the other mpv messages), Up and Down scroll the page by half a window, so a message taller than a short window can be read to the end with the controller. Those messages on a first launch have Look again focused (the mpv missing screen) and scroll the same way. Everywhere else they move the focus as before.
- **Messages keep the focus in view:** when "Playing…", "Rescanning…" or an error appears above the lists, the focused tab, tile or row is scrolled back into view if it was pushed under the hint bar.
- **Gap in the design system:** at Enamel's smallest box (320 by 240) the remove question's picker is taller than the room above the hint bar, so its top is cut off. Raised for Enamel (the responsive layout work, `needs enamel`); not restyled here.
- **Text** follows Enamel's sizes, which don't grow with a narrower page. The wordmark is the one thing fitted to the page's width, so KETTLE stays on one line.
- **Follow the space, not a device:** the top bar was 6% of the window's height (at least 40px) until the Home actions work made it Enamel's action bar, which is its own height; the letter strip's letters fit the space between the bars.
- **Tokens removed:** `--continue-tile-height`, `--continue-small-tile-height`, `--continue-ring-room` (Enamel's tile sizes and `--en-c-shelf-room` replace them). No class name or `data-` hook changed.

**Checks:** the browser checks run at six window sizes, labelled by width only (`tests/window_sizes.py`: 320 by 240, then 640, 1024, 1280, 1920 and 2560 wide; below Firefox's narrowest window, 500 pixels, the page is zoomed in so it lays out at that width), with screenshots at each in `docs/screenshots/design-system/`. At each width, `tests/design_system_check.py` (loading, first launch, the messages) and `tests/design_system_lists_check.py` (Continue watching, both lists, the remove question, a show's episodes) check: no sideways scrolling, nothing cut off, focus rings never clipped, the focused row never under the tab strip or the hint bar, exactly one focused element. `tests/continue_watching_check.py` checks that the tiles take Enamel's widths and that a wider row shows more of them. `tests/test_no_layout_targets.py` (unit tests) fails if the interface files, these docs, the /next instructions or the browser checks name a screen's aspect ratio or tie a device to a screen size.

## Fresh start for testing (the fresh start mode)

Two launch options for testing, for the designer and anyone testing first-launch screens. Both are environment variables, set in a Steam shortcut's launch options (`KETTLE_FRESH_START=1 %command%`); `launch.sh` passes them on unchanged, so it needs no change. `1`, `true`, `yes` or `on` turn one on; anything else, or leaving it out, is normal use. Steps for a second Steam shortcut are in the README, "Testing as a brand-new user".

**One data folder.** The app finds its data folder in one place, once, at launch: `backend/launch_options.py`. In normal use that is the folder `settings.json`'s `data_dir` names (`data/` in the app folder unless it says otherwise), exactly as before; every part of the app (the saved library, Continue watching and its pictures) reads and writes its data only there.

**What the app remembers between launches** (the audit, posted on the fresh start mode): the settings (`settings.json`), the saved library (`<data_dir>/library.json`), the Continue watching list and its pictures (`<data_dir>/continue.json`, `<data_dir>/thumbnails/`), and the logs (`logs/`). Outside the app's folder: resume positions are mpv's own, in mpv's `watch_later` folder (`~/.var/app/io.mpv.Mpv/.local/state/mpv/watch_later/` for the Flatpak mpv, `~/.local/state/mpv/watch_later/` otherwise), and Firefox keeps its own profile for the app, `kettle-video-profile` (the page stores nothing in it; the profile used before the rename to Kettle Video, the Kettle Video rename, is no longer used and never touched). mpv's control socket and the frame mpv saves on quit live in short-lived folders under `/tmp`.

**`KETTLE_FRESH_START=1`: open as a brand-new user would.**
- At launch the app makes a new, empty folder `/tmp/kettle-fresh-…` (readable by this user only) holding a mark file, an empty `data` folder used as the data folder, and an empty `watch_later` folder that mpv is told to use for its resume positions (`--watch-later-dir`, given after `mpv_args` so it always wins; the designer's choice on the fresh start mode). `/tmp` because the Flatpak mpv can write only there.
- **Both folders count as not set** (the fresh start onboarding work), whatever `settings.json` says, so onboarding shows at launch, as for someone new (see "Onboarding: choosing the folders"). The search for folders and the rest of the flow work as usual and read the real folders on the device, read-only. Once they are chosen, the first scan and its result follow, as for a new user (the first scan screen), and scanning and playing use them for that session.
- **The folders chosen last that session only.** Onboarding saves them to a `settings.json` in the temporary folder, created then, holding only those two keys and never read back; the app is using them already. That is the only file it can save to in fresh start, so nothing in the session reaches the real `settings.json`: not a choice from "Browse somewhere else", not a failed save, which says what it always says, with the choice still open. The real file stays byte-for-byte unchanged, and isn't created if there is none.
- **Every other setting** (`mpv_command`, `mpv_args`, `keep_awake`, `resume`, and so on) is still read from the real `settings.json`, as the developer options are read from it. A mistake in the real file still stops a fresh start with its sentence, before any temporary folder is made. The real data folder, wherever `data_dir` puts it, isn't protected from being chosen as a media folder in fresh start, as it isn't in use there and nothing is written to it.
- So resume and Continue watching work within the session, and the real data folder and mpv's real resume positions are never read or written. The logs still go to `logs/`, since they are what a bug report needs. The Firefox profile is shared.
- When the app quits (Quit, B, the window closed, or Steam's stop signal) the folder is deleted, with the folders chosen, so the next fresh start asks again. If it is left behind (a crash, or a forced stop), the next fresh start deletes it first.
- **The one delete this adds**, and how narrow it is: only a folder directly in `/tmp`, named `kettle-fresh-…`, a real folder (not a link), owned by this user, holding the mark file the app writes (its first line and the process number of the copy that made it), and not in use by a copy of the app still running. Nothing else is ever deleted.

**`KETTLE_PRETEND_NO_MPV=1`: behave as if mpv were not installed.** The mpv check (`/api/mpv-status`, and the check before playing) answers exactly as on a device without mpv, so the "mpv not found" screen shows with the install hint. Nothing is uninstalled. Works alone or with fresh start (`KETTLE_FRESH_START=1 KETTLE_PRETEND_NO_MPV=1 %command%`). With fresh start it is a first launch, so the screen has Look again (the mpv missing screen), which stays on this screen because mpv still counts as missing. Alone, with folders already set, it is a later launch and has no button.

**The marker.** In fresh start the page shows FRESH START on every screen: Enamel's hint (`.en-hint`) with no button glyph, first in the hint bar, at its start, so it sits in the bottom-left corner while the hints keep the right; like any hint it wraps onto its own line when they don't all fit, so it never covers one. The loading screen covers the hint bar, so it has its own marker in the same corner. It is never focusable. ## Size readout (the sizing spike)

A developer-only option, off unless `settings.json` has `"debug_size_readout": true` (`false` or leaving it out is normal use; anything else is a plain settings message). It is not in `settings.example.json`; setup is in `docs/device-setup.md`, section 6. It changes nothing on screen.

At start the page measures, once, the window's size in CSS pixels, the device pixel ratio and the screen's size, and sends them to `POST /api/size-readout`. The backend checks each one is a plausible number and writes one line to the launch log, for example:

`size readout: window 1280x800 CSS px; device pixel ratio 1; screen 1280x800 CSS px = 1280x800 screen px; Firefox zoom: part of the device pixel ratio (Firefox doesn't report it separately)`

Firefox gives a page no zoom value of its own: its zoom is folded into the device pixel ratio, so the line says so rather than inventing a number (see `docs/decisions.md`). The numbers are only reported: no layout uses them (`ui/js/size_readout.js` is the one script allowed to read the screen's size, and it changes nothing on the page). What the readout and the captures showed is in `docs/sizing-report.md`.

## Onboarding: finding the folders (the folder finder)

Part 1 of onboarding, with no screen yet: the backend looks for the folders that hold videos, so the next screens (the folder choice screens) can offer them without the person typing a path. The rules are the storage spike's (`docs/spikes/storage.md`, Questions 1 to 3 and "What would stop onboarding"), in `backend/folder_finder.py`. It only reads: it never creates, moves, renames or deletes anything.

- **Places:** internal storage (the home folder only), then every card or USB drive that is really mounted, that is, in the system's list of mounts (`/proc/self/mountinfo`) under `/run/media/`, `/media/` or `/mnt/`, in the order of where they are mounted. A folder left behind where a card was (the Nova keeps one) is not a mount, so it is not offered. The kind of drive comes from where it sits in the hardware tree (`/sys`), as in the spike, including the btrfs fix.
- **Names:** "Internal storage", "SD card", "USB drive" ("Other drive" when the hardware can't tell), with a number for a second of the same kind ("SD card 2"; an internal drive mounted there is "Internal storage 2"). The card's own label is never shown.
- **State of each place:** `ok`; `not_ready`, a card or drive whose folder exists but can't be read (the Deck, for a moment after a card goes in), never "empty"; `unreadable`, internal storage that can't be read; `partial`, when the search ran out of time (10 seconds for all places together; what was read by then is kept). A folder that can't be read deeper down, or a card pulled out mid-search, just adds nothing.
- **Where it looks:** up to 6 levels below each place's top, never into hidden folders, Steam's (`steamapps`, `SteamLibrary`, `Steam`, `compatdata`, `shadercache`), emulators' (`Emulation`, `EmuDeck`, `ES-DE`, `RetroArch`, `roms`, `downloaded_media`, `Applications`, `homebrew`) or junk (`Sample`, `Samples`, `lost+found`, and `._` files), ignoring capitals. Links are not followed.
- **Which folders:** the folder that holds the films or shows, never one film's own folder: from each top-level folder with videos, go down while there is only one way down, but never into a single title; a folder holding two or more collections is split into them; season-like folders (`Season 1`, `S02`, `Specials`, `Extras`, `Disc 1`, `Part 2`) belong to their show. Videos at a place's top suggest the place itself (`whole_place`, with an empty `name`). A folder whose videos are all under 20 MB (trailers, previews, game intros) is not suggested.
- **For each folder:** `id` (a short fingerprint of its location: the same folder gets the same id every time, and the id gives the location away to no one); `place` (the place's name); `name` (its own name); `trail` (the folder names from the place's top down to it, for "SD card › Media › Films"); `videos` and `folders` (how many videos, and how many folders hold them directly); `count_text` ("62 videos", "1 video", "31 videos in 4 folders"); and `examples`, up to two names from inside it in name order: its titles' folders and loose videos (without the extension), for a show's own folder its episodes, for a whole place only the videos at its top. Since the first onboarding review fixes also `problem`: the sentence saying why it can't be chosen, or null.
- **What was checked**, `checked`: one sentence naming each place and any state, ending in ", and no SD card found" when there is no card: "Internal storage, and no SD card found", "Internal storage and SD card (not ready yet)". `sd_card_found` says whether a card was there at all. Since the first onboarding review fixes also `gaps`: the line above the list on screens 1 and 2 when the search didn't see everything, or empty.
- **Privacy:** full paths stay in the backend: the server keeps every folder found this session to look its path up by its id (the folder choice screens picks by id). The launch log gets one line with counts and kinds of place only (`onboarding: looked for folders in 2 places (internal ok, sd ok), found 2 folders in 0.005 s`), never a path or a name.

**Checks:** `tests/test_folder_finder.py` (the spike's layouts, clips, depth, skip names; places from the list of mounts and the hardware tree; not ready and unreadable places, a card gone before the search, the time limit; ids; counts and examples; the `checked` wording; no full path in the answer, the log line or the server's response; the folders byte-for-byte unchanged after a search). Run read-only against the real SD card on the Deck: the same two folders as the report, in a few milliseconds, the card unchanged.

## Start-up problems on screen (the start-up problem screen)

Never fail silently, also before the app is up (audit finding H3). When Kettle can't start, the launcher says why on screen instead of only in the log:

| What went wrong | What the launcher logs | What the screen says (after "Kettle couldn't start.") |
|---|---|---|
| No Firefox (neither on the system nor as the Flatpak) | `firefox not found …` | Kettle shows its screens in Firefox, and Firefox isn't installed. Install Firefox from Discover in Desktop Mode, then start Kettle again. |
| The server stopped while starting, because of a mistake in `settings.json` | the server's `Settings error: …`, then `backend exited early …` | Your settings have a mistake: (the settings reader's own sentence). Fix it in settings.json, in Kettle's folder, then start Kettle again. |
| The server stopped while starting, for any other reason | `backend exited early …` | Kettle stopped while it was getting ready. Start Kettle again. |
| The server never answered (10 seconds) | `backend never opened its port …` | Kettle took too long to get ready. Start Kettle again. If it keeps happening, restart the device. |

Every message ends with the log's own name (never a full path): "The details are in launch-….log, in the logs folder in Kettle's folder. Attach it if you report this on GitHub." The launcher also logs `showing the start-up problem on screen (<reason>)`.

**How it shows.** With Firefox, a small message server (`backend/startup_error.py`, standard library only; it uses nothing from the app but the settings reader, so whatever stopped the app can't stop it too) serves `ui/startup-error.html` on a free port, and the launcher opens it in the same kiosk window and profile as the app. It is built like the "mpv not found" screen: the lines in the app's `.full-message` box, Enamel's primary button Close (focused, kept in view), and the hint bar with A Close and B Close. A (Space), B (q), Enter, Escape or a tap on Close closes it: the page tells the server, the server ends, and the launcher closes Firefox as it does when the app quits. Up and Down scroll, so every line can be read in a small window. With no Firefox, the same words go into a system dialog the device already has: zenity (part of SteamOS), else kdialog; A presses its OK. With neither, only the log has it. Nothing is installed or added.

**Order of the launch:** the launcher now looks for Firefox before it starts the server (so a missing Firefox is said at once); everything else in a normal launch is unchanged.

**Code and checks:** `launch.sh` (`show_startup_error`, `show_startup_dialog`, `start_firefox`), `backend/startup_error.py`, `ui/startup-error.html`, `ui/js/startup_error.js`. `tests/test_startup_error.py` (unit tests: scripted launcher runs with stand-ins for Firefox, zenity and flatpak, for Firefox missing, a broken settings file, a server that never answers and a normal launch; the words; the message server only serving its own files to its own address) and `tests/startup_error_check.py` (the page in a headless Firefox at every window width, and each way of closing it).

## Installing (the installer work)

- **One command, no password.** `bash install.sh` in Desktop Mode, with the release's `kettle-video-<version>.tar.gz` and its `.sha256` beside it (or the archive named on the command line). Never `sudo`, never a system change, never Steam's own files. Run as root, it stops.
- **Checked before anything is placed.** The archive must match its checksum and hold one top folder with no path outside it, and must be a Kettle Video release (`launch.sh`, `backend/server.py`, `VERSION`); otherwise it stops with "Nothing was installed or changed."
- **Places** (the designer's decision on the installer work), each moved by its XDG variable when that is an absolute path: app files `~/.local/share/kettle-video/app` (replaced by a later install or update; since the installer's update step a shortcut to the current version's folder, see "Updating"), data `~/.local/share/kettle-video/data`, settings `~/.config/kettle-video/settings.json` (made by onboarding on the first launch), logs `~/.local/state/kettle-video/logs`, menu entry `~/.local/share/applications/kettle-video.desktop` with `Icon=` the app's `ui/kettle-video.png`. A folder at the app's place without the installer's mark is never touched: the install stops. The menu entry is written only when it is missing or already holds `Exec="<app>/launch.sh"`; any other entry with that name (such as one an older `install-shortcut.sh` made for a development copy) is left as it is, with a warning saying how to move it, and the summary says the app wasn't added to the menu; the install still finishes (the installer review fixes, see "Menu entries" below).
- **Installed or development copy.** The installer leaves the mark file `INSTALL_MARK` (`installer/names.env`) in the app folder. `backend/app_paths.py` then gives the settings reader, the server and the start-up message the places above; a `data_dir` that is relative counts from `~/.local/share/kettle-video`. Without the mark (the git folder on the Deck and the Nova) `settings.json`, `data/` and `logs/` stay in the app folder as before. `python3 -m backend.app_paths logs` prints the copy's logs folder; `launch.sh` writes its launch log, Firefox log, `launch.lock` and Flatpak instance file there, or in `logs/` if that answer fails.
- **mpv.** A system `mpv`, else the Flatpak (`flatpak info io.mpv.Mpv`). If missing: why it's needed, the one command `flatpak install flathub io.mpv.Mpv`, and "Install mpv now with that command? [y/N]". Only a yes runs it; a no, no answer, no Flatpak or a failed install finishes anyway (the app shows "mpv not found"), and the summary adds the per-user commands (`flatpak remote-add --user --if-not-exists flathub …`, `flatpak install --user flathub io.mpv.Mpv`).
- **Summary.** What it did, where each thing lives, the mpv state, then the Steam steps: app menu, right-click Kettle Video, Add to Steam (when the menu entry wasn't added, the installer review fixes: they say not to add the menu's Kettle Video, how to move a development copy's entry and run the installer again, or to add `<app>/launch.sh` with Steam's Browse instead); in Gaming Mode set the controller layout again (Steam keeps one per shortcut).
- **Names** all come from `installer/names.env`. The release script (`tools/release.py`) writes `install.sh` next to the archive with those lines written into its `# --- names ---` block, and `installer/update.py` written into its `# --- update logic ---` block (the installer's update step), so it needs no other file.

## Updating (the installer's update step)

Running the installer again with a newer release updates the installed copy. The work is done by one shared step, `installer/update.py` (standard library only, importing nothing from the app), which `install.sh` runs for a first install and for an update, and which the app's "Update and restart" (the Update and restart work) is to call as well, so the checks and the rollback exist once. Its exit status: 0 installed or updated, 1 stopped with nothing changed, 2 rolled back, 3 the person said no to an older version.

- **Layout.** Each version is unpacked into its own folder, `~/.local/share/kettle-video/versions/<version>-<6 random letters>`, and the app folder `~/.local/share/kettle-video/app` is a shortcut (symlink) to the current one. The menu entry, the Steam shortcut and `backend/app_paths.py` all go through `app`, so nothing else changes. Switching versions is one rename of that shortcut.
- **Checked before anything changes.** The archive's bytes are checked against its `.sha256`, then its entries (one top folder; only files, folders and shortcuts pointing inside it). The bytes checked are the bytes unpacked. A folder at the app's place that the installer didn't make, or a second install or update already running, stops it too. A stop says "Update stopped: <why>" and "Nothing was changed: Kettle Video <version> is still installed." (on a first install, "Install stopped" and "Nothing was installed or changed.").
- **Versions.** It prints "Installed now: Kettle Video <old>" and "This archive: Kettle Video <new>" (versions compared by their numbers, with a pre-release such as `0.2.0-dev` before `0.2.0`). An older archive gets a warning and "Install <new> anyway? [y/N]"; anything but yes changes nothing. The same version is put in again without asking.
- **Order.** Unpack into `versions/` beside the installed version; write the mark file; flush everything to disk; switch the shortcut; flush again; check the first start; only then remove the previous version (and anything an interrupted run left in `versions/`).
- **Started cleanly** (decided on the installer's update step; checked with no person needed): the new version's server (`python3 -m backend.server`, from the app folder, on a free port) reads the person's own settings file without a mistake, starts and keeps running; within 30 seconds its page (`/`) answers with HTML; every stylesheet and script the page links answers; and `/api/onboarding` answers. It is then asked to close (`/api/shutdown`). It runs as a fresh start (`KETTLE_FRESH_START=1`, see "Fresh start for testing"): its data folder is an empty temporary one, deleted when it closes, so the person's data folder is never opened (a normal start tidies Continue watching's list and pictures there). No window opens, nothing plays or is scanned, the settings file is only read, and launch options that would change the start (pretend no mpv, the developer update, the size readout) are left out. Only an update is checked: a first install has nothing to go back to.
- **Rollback.** If unpacking, switching or the first start fails, the shortcut is pointed back at the previous version and the new folder removed: "The update to <new> didn't work: <why>" and "Rolled back: Kettle Video <old> is installed again, as it was. Your settings, library and logs were not touched." Settings, data and logs are never written, moved or removed, whatever the outcome.
- **Power cut.** At any moment the app folder is the old version or the new one, complete. A run cut short leaves a folder in `versions/` that the next run removes. The one exception is the first update of an install made before this layout (the installer work's plain `app` folder): it is moved into `versions/` and then replaced by the shortcut, two renames one after the other; a power cut exactly between them leaves no `app` until the installer is run again, which then installs as new.
- **Installer.** `install.sh` hands the archive to the step and stops with its exit status on anything but success; then the folders, menu entry, mpv check and summary follow as for an install, with the summary saying "<old> before, <new> now".

## Uninstalling (the uninstaller work)

`installer/uninstall.sh` ships inside the app (the release archive carries `installer/`), so an installed copy runs `bash ~/.local/share/kettle-video/app/installer/uninstall.sh`. Bash, no `sudo`, no new dependency; it reads `installer/names.env` beside it and nothing from the app.

- **Places**, never from a typed path or a guess: `APP_ID`, `DESKTOP_ENTRY`, `INSTALL_MARK` and `FIREFOX_PROFILE` from `names.env`, in the same standard folders as the installer (each XDG variable used only when it is an absolute path).
- **App files** (always removed): `app` and `versions/` in `~/.local/share/kettle-video`, the menu entry `~/.local/share/applications/kettle-video.desktop` when it holds `Exec="<app>/launch.sh"` (any other entry with that name, such as an older development copy's, is left as it is, the list says so and the uninstall carries on; the installer review fixes), and the kiosk window's Firefox profile `FIREFOX_PROFILE` in `~/.mozilla` and in `~/.var/app/org.mozilla.firefox/data` (the designer's decision on the uninstaller work: it counts as app files; `launch.sh` rebuilds it at every launch, and its `PROFILE_NAME` must match `names.env`, which a test checks). The profile from before the rename (the Kettle Video rename) is never touched. `~/.local/share/kettle-video` is removed only if it ends up empty.
- **Data** (kept unless asked): `data/`, the settings folder `~/.config/kettle-video` and the logs `~/.local/state/kettle-video/logs` (decided on the uninstaller work: settings and logs count as data). Removed only after "Also delete your library, settings and logs? [y/N]" and then a second "Delete your library, settings and logs? [y/N]" after the list and "it can't be undone"; anything but yes keeps them. mpv's own resume positions belong to mpv and are never touched.
- **Checked before anything is removed**, otherwise "Uninstall stopped: <why>" and "Nothing was removed.": not run as root; every place resolves (shortcuts followed) inside the home folder; `app` is a shortcut of the form `versions/<folder>` or a folder holding the mark; `versions/`, the profiles and the data folders are real folders, not shortcuts; neither media folder in the settings file (`movies_path`, `tv_path`) is inside anything to be removed; the app isn't open (`launch.lock` in the logs folder is free) and no install or update holds `versions/`. A missing app folder stops it ("isn't installed here"); a missing menu entry, profile or `versions/` is simply skipped, so a second run finishes an uninstall that stopped part way (`versions/` goes before the `app` shortcut for that reason).
- **Questions.** It lists what it removes and keeps, then "Uninstall Kettle Video? [y/N]"; anything but yes (or no answer) removes nothing.
- **Summary.** "Done. Kettle Video is uninstalled.", whether the data was kept or deleted, "mpv is still installed.", and the Steam reminder: remove the shortcut by hand (right-click it in the Steam Library, Manage, Remove non-Steam game from your library); Steam's files are never written.

## Menu entries: a development copy and an installed copy (the installer review fixes)

Each copy has its own app menu entry, so neither takes over, nor removes, the other's. Both names are in `installer/names.env`.

- **Installed copy**: `DESKTOP_ENTRY` (`kettle-video.desktop`), named "Kettle Video", written by `installer/install.sh` (see "Installing") and removed by `installer/uninstall.sh` only when it starts the installed copy.
- **Development copy**: `DEV_DESKTOP_ENTRY` (`kettle-video-dev.desktop`), named "Kettle Video (dev)", written by `install-shortcut.sh` with `Exec=<the copy's folder>/launch.sh`. Before the installer review fixes that script wrote `kettle-video.desktop`; when it finds that file holding exactly its own `Exec=` line, it removes it after writing the new one. Any other `kettle-video.desktop` is never touched. In a folder holding the install mark it writes nothing and says the installed copy already has its entry.
- The installer and uninstaller never read or write `DEV_DESKTOP_ENTRY`. Steam shortcuts already made keep working: they point at `launch.sh`, not at the entry.
